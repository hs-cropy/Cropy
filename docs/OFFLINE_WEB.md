2026-10-28 Figma 모바일 화면에 맞춰 정리. 오프라인 화면은 한 페이지(`index.html`)를 주소의 `#`으로 네 화면으로 나눈다(`core.mjs`의 `viewFromHash`). 화면 전환은 오프라인에서도 동작한다.

| 화면 | 주소 | 내용 |
|---|---|---|
| 오프라인 사용 준비 | `#prepare`(기본) | 준비 상태 카드만 보인다 |
| 새 진단 | `#new` (예전 `#analyze`) | 작물 선택·사진 고르기·이 기기에서 진단하기. 준비된 모델이 없으면 준비 화면으로 돌아간다 |
| 진단 결과 | `#result` | 진단 결과와 추가 촬영. 결과가 없으면 빈 안내("사진으로 작물 상태를 확인해보세요", 768px 이상은 "먼저 작물 사진을 준비해주세요")와 새 진단 시작하기(온라인 `DiagnosisEmptyState.tsx`, 촬영 방법 링크는 뺀다). 모델 없이도 기록의 결과를 볼 수 있다 |
| 진단 기록 | `#records` | 기기 기록 목록 |

- 내비는 온라인 앱과 같은 세 탭이다: 헤더 **새 진단**·**진단 결과**·**진단 이력**, 하단 **촬영**·**진단**·**이력**이 각각 `#new`·`#result`·`#records`로 간다. 준비 화면에서는 새 진단 탭이 켜진다. 온라인 촬영 화면(`/home`)이나 서버 이력(`/history`)으로 가는 링크는 오프라인 화면에 두지 않아, 오프라인 화면(`index.html`)의 내비는 인터넷 없이 모두 열린다. 설치 안내(`install.html`)의 헤더 내비와 "웹에서 계속하기"는 온라인에서 쓰는 화면이라 온라인 주소를 그대로 쓴다.
- 이동 규칙: 준비 완료의 **진단 시작**은 새 진단으로 가서 사진 고르기를 연다. 진단이 끝나면 진단 결과로 옮기고(분석 중 다른 탭으로 갔으면 그대로 둔다) 진단한 사진은 내린다. 진단 결과의 **새 사진으로 진단하기**와 빈 안내의 **새 진단 시작하기**는 새 진단으로 가서 사진 고르기를 연다. 진단 기록의 **결과 보기**는 진단 결과로 간다. 새 진단 화면에서 새 진단 탭을 다시 누르면 떠 있던 진단 실패 카드를 닫는다. 분석 중 다른 탭으로 갔다가 실패하면 토스트로 알리고, 카드는 새 진단 탭에 돌아오면 보인다. 새 결과가 나오거나 보던 결과를 지우면 추가 사진 확인 실패 카드도 내린다.
- 설치 안내는 설치창에서 수락하면 "설치하는 중이에요" 문구만 보이고, 설치 완료 화면은 실제 설치가 끝났을 때 오는 `appinstalled`에서만 보인다. 15초 안에 `appinstalled`가 오지 않으면 홈 화면을 먼저 확인하고, 앱이 없으면 브라우저 메뉴에서 설치하도록 안내한다(늦게 온 `appinstalled`도 완료 화면을 보인다). 기다리는 동안 설치창을 다시 열 수 있게 되면 바로 다시 시도할 수 있다.
- 진단 결과는 온라인 결과 화면(`DiagnosisResultView.tsx`)과 같은 구성이다. 머리는 "진단 결과"와 결과 마스코트다. 좁은 화면(1024px 미만)은 요약 카드(사진·작물·병명·등급 배지·신뢰도), 지금 해야 할 일, 상세 정보(증상·원인·예방법) 순서다. 넓은 화면은 왼쪽 사진·정보 카드와 오른쪽 병명·3열 할 일·상세 정보의 2열이고, 부제는 진단 시각 문장이다. 결과는 새 진단을 할 때까지 진단 결과 탭에 남고, 지난 결과는 진단 기록의 결과 보기로 다시 본다. 후보 목록과 등록 농약은 온라인 결과처럼 보이지 않는다. 판별 불가(`category: other`)는 병해 결과가 아니라 등급·신뢰도·관리 안내 없이 "작물 잎을 찾지 못했어요"와 촬영 방법, **다시 촬영하기**만 보인다. 등급 배지와 시각 문장은 `core.mjs`의 `gradeOf`·`resultTimeSentence`가 온라인과 같은 규칙으로 만든다.
- 실행 환경·모델·사진 처리 실패는 분석 실패 카드(다시 분석·다른 사진)로 보인다. 진단 실패는 새 진단 화면에, 추가 사진 확인 실패는 진단 결과 화면에 뜨고, 다른 탭에서는 보이지 않는다. 사진 형식·용량·해상도 문제는 문구로만 알린다.
- 기기 저장에 성공하면 "이 기기에 저장했어요." 토스트를 보이고, 새 사진을 고를 때까지 진단 결과·진단 기록 화면 머리에 "기기 저장 완료" 라벨을 보인다(진단 결과 화면은 방금 저장한 기록의 결과를 볼 때만이고, 안내 카드가 있으면 카드의 라벨이 먼저다). 진단 기록 화면은 들어올 때마다, 그리고 그 화면에서 진단 이력을 다시 누를 때 기기의 기록을 다시 읽는다. 기록 저장 공간 부족, 서버 동기화 실패, 연결 없는 동기화 대기는 진단 기록 화면의 안내 카드로 보인다(`recordsNotice`).
- 다운로드 중에는 버튼이 없다. 연결이 끊기거나 30초 동안 받은 데이터가 없으면 받기를 끊고 다운로드 중단 화면("연결 필요")에서 다시 받는다. 모델이 이미 있으면 기존 모델로 준비 완료를 유지한다.
- 준비가 끝난 기기는 연결돼 있을 때 서버 `manifest.json`의 `version`을 비교한다(`updateAvailable`). 다르면 업데이트 다이얼로그를 띄우고, 나중에(또는 Esc)를 누르거나 업데이트에 실패하면 이번 접속 동안 다시 묻지 않는다. 새로 열면 다시 묻는다.
- 설치 안내의 하단 이동 버튼은 휴대폰 화면 아래에 붙는다. 아이폰 안내에는 Safari에서 바로 받는 링크를 두지 않고, 홈 화면에 추가한 앱에서 받도록 안내한다.

## 실행 방식

| 방식 | 사진 분석 | 기록 저장 | 인터넷 없이 필요한 연결 |
|---|---|---|---|
| Orange Pi 로컬 서버 | 기존 FastAPI/PyTorch 모델 | 보드의 SQLite와 업로드 폴더 | 휴대폰↔보드의 로컬 Wi-Fi/LAN 연결 |
| 스마트폰 브라우저 자체 실행 | ONNX Runtime Web, WASM CPU | 해당 브라우저·오리진의 IndexedDB | 준비 후 서버 연결도 필요 없음 |

브라우저 자체 실행은 처음에 페이지·약 94MB 모델·약 14MB WASM 런타임을 받아야 한다. 준비 파일은 인터넷이나 로컬 보드에서 받을 수 있다. 모델 SHA-256·파일 크기·세션 생성이 모두 성공한 뒤 저장된 모델을 교체한다. 연결 중단·업데이트 실패 시 기존 모델을 유지한다. 새 묶음은 서버 manifest 의 `version`이 받아 둔 묶음과 다를 때 업데이트 다이얼로그로 알린다. 진단 모델(CNN) 다운로드 재개는 처음부터 다시 받는 방식이다. 음성 질문용 기능 선택 모델은 파일 단위로 이어 받는다(아래 "기능 선택 모델 묶음").

Service Worker와 모델 준비에는 HTTPS가 필요하다. 개발용 localhost/127.0.0.1 예외와 달리 휴대폰에서 `http://보드IP:3000`으로 접속하면 자체 오프라인 준비는 지원하지 않는다. 이 주소의 기존 **서버 진단**은 계속 사용할 수 있다. 자체 실행을 제공할 때는 휴대폰이 신뢰하는 인증서와 HTTPS 프록시를 구성해야 한다. [MDN 보안 컨텍스트](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)

## 모델 준비

모델 변환은 개발 PC에서 한다. backend의 기존 검증을 통과한 `ml/checkpoints/best_model.pth`가 필요하다. 체크포인트와 ONNX 파일은 대용량 산출물이므로 Git에 포함하지 않는다.

```powershell
cd backend
.venv/Scripts/python.exe -m pip install -r requirements-browser-export.txt
.venv/Scripts/python.exe scripts/export_browser_model.py
cd ../frontend
npm ci
npm run build
```

생성물은 `frontend/public/offline-assets/`의 `cnn-<hash>.onnx`, `manifest.json`, `manifest-<bundle version>.json`이다. 묶음 버전은 모델·전처리·병해 안내·판단 기준을 포함한다. 이전 manifest 아카이브는 이전 기기 기록 동기화에 필요하므로 유지한다. ONNX 모델의 hash와 묶음 버전은 서로 다르다. JS/WASM은 빌드 시 같은 npm 패키지에서 `public/offline-runtime/`으로 복사하고 `sw.js`의 `SHELL` 목록(화면·스크립트·로고·배경·마스코트) 파일 hash에 따라 Service Worker 캐시 이름을 갱신한다. 목록에 넣은 파일이 없으면 이 단계에서 멈춘다. 외부 CDN을 사용하지 않는다. [ONNX Runtime Web 배포 안내](https://onnxruntime.ai/docs/tutorials/web/deploy.html)

Docker Compose는 프론트 이미지에 public 파일을 포함하고 백엔드에 동일한 offline-assets 폴더를 읽기 전용으로 마운트한다. **모델을 준비한 뒤** 이미지를 빌드해야 한다. 백엔드 `OFFLINE_BUNDLE_DIR`는 Compose에서 `/offline-assets`다. 모델 파일·manifest 아카이브를 포함한 폴더를 배포 대상에도 복사한다.

### 기능 선택 모델 묶음 (#166)

음성 질문의 기능 선택 모델은 기기마다 다르다. 휴대폰(iPhone·안드로이드)은 소형 분류기 `mobile_clf`(약 15MB), WebGPU가 있는 PC는 Qwen q4f16 `web_qwen`(약 1.34GB)을 받는다. 그 밖의 기기(WebGPU 없는 PC 등)는 받을 파일이 없고 서버가 고른다(`core.mjs`의 `functionBundleKind`). 모델 파일은 ML 산출물(PR #176 `ml/qwen`)에서 가져와 등록한다.

```powershell
cd backend
.venv/Scripts/python.exe scripts/export_browser_model.py --function-bundle mobile_clf=<분류기 폴더> --function-bundle web_qwen=<web_onnx/2b 폴더>
```

- `mobile_clf` 폴더에는 `model_int8.onnx`·`tokenizer.json`·`tokenizer_config.json`·`labels.json`이 있어야 한다. `web_qwen` 폴더는 `files.json`(`[[이름, 바이트], ...]`)에 적힌 파일과 `prefix_q4f16.json`·`prefix_q4f16.bin`이 있어야 하고, 크기가 `files.json`과 다르면 멈춘다.
- 스크립트는 파일마다 SHA-256을 계산해 `offline-assets/function/<kind>/<version 앞 16자>/`에 복사하고 `offline-assets/function-models.json`을 원자적으로 교체한다. 묶음 `version`은 파일 목록(이름·크기·SHA-256)의 해시다. CNN `manifest.json`과 파일을 나눠 두므로 기능 선택 모델만 바뀌어도 CNN 업데이트 다이얼로그가 뜨지 않는다.
- `GET /api/v1/offline/manifest`는 `function-models.json`이 있으면 `function_models`로 합쳐 준다. 오프라인 화면은 CNN처럼 정적 파일 `/offline-assets/function-models.json`을 직접 읽는다.
- 오프라인 화면은 진단 파일이 준비된 뒤 **음성 질문 파일 (선택)** 카드를 보인다. 받기 전에 기기 종류와 `navigator.storage.estimate()`로 크기·Wi-Fi·저장 공간 안내를 바꾼다. 파일마다 크기와 SHA-256을 확인한 뒤에만 Cache Storage `transformers-cache`에 넣으므로 검증에 실패한 파일은 남지 않는다. 키는 파일 주소(`<origin><base_url>/<name>`)다. #167·#168에서 transformers.js가 같은 주소로 요청하면 네트워크 없이 캐시에서 읽는다. 다 받으면 IndexedDB `assets`의 `fn:<kind>`에 묶음 정보를 적고 이전 버전 파일을 지운다. 연결이 끊기면 다시 받을 때 이미 받은 파일을 건너뛴다. 브라우저가 캐시를 지웠으면(특히 iOS) 다시 받기를 보인다.
- 아직 이 파일로 기능을 고르는 코드는 없다(#167 휴대폰 분류기, #168 PC Qwen). 묶음이 없으면 카드를 숨긴다.
- Docker: 프론트 이미지는 빌드 시점의 public 파일을 서빙하므로(Next.js는 빌드 뒤 public에 추가한 파일을 서빙하지 않는다) 묶음을 등록한 뒤 이미지를 빌드해야 한다. `web_qwen`을 넣으면 이미지가 약 1.34GB 커진다. 새 버전을 등록해도 이전 `function/<kind>/<version>/` 폴더는 남는다(받는 중인 기기가 있을 수 있어서다). 이미지를 빌드하기 전에 `function-models.json`의 `base_url`에 없는 버전 폴더를 지운다.

인터넷이 없는 보드에 배포할 때는 필요한 아키텍처의 Docker 이미지와 모델 파일을 미리 준비해 가져간다. 실행 중 npm/pip 설치나 외부 모델 다운로드는 필요하지 않지만, 이 작업에서 Orange Pi 장치 자체의 설치·속도는 검증하지 않았다.

## 사용자 흐름

1. 연결된 상태에서 설치 안내의 **오프라인 파일 받기**를 누르거나, 오프라인 사용 준비 화면의 **다시 다운로드**를 누른다. 새 파일이 나오면 업데이트 다이얼로그의 **업데이트**로 받는다.
2. 준비 완료 후 **진단 시작**을 눌러 새 진단 화면에서 JPEG/PNG 사진과 작물을 선택해 기기에서 진단한다(결과는 진단 결과 화면에 보인다). 파일은 기본 10MiB 이하, 4천만 픽셀 이하로 제한한다.
3. 기기 이력에 결과·원본 사진·원래 예측 분포·모델/묶음 버전을 저장한다. 혼동쌍이면 안내 부위의 두 번째 사진을 분석하고 두 분포를 0.4:0.6으로 융합한다. S1/S2 시안의 고정 신뢰도나 처리 시간을 강제로 만들지 않는다.
4. 연결 없이 새로고침하고 같은 기기 이력을 확인하거나 새 진단을 할 수 있다.
5. 서버 연결 후 이력의 **서버에 저장**을 누르면 해당 기록을 전송한다. 자동 업로드하지 않는다. 서버는 파일·전체 9클래스 확률·촬영 시각·지원 묶음 버전을 검증하고 당시 묶음의 안내를 저장한다. 기기 결과를 서버에서 다시 추론하지 않으며 `prediction_mode=browser`로 출처를 표시한다.
6. 서버 전송을 시작하기 전에 전송 시도 표시를 기기에 저장한다. 응답 유실도 저장 성공일 수 있으므로 전송한 기록의 사진·분포를 보존하고 재촬영을 잠근다. 동일 결과로 다시 전송하면 멱등 응답으로 성공 여부를 확인한다. 추가 사진은 새 진단으로 저장한다.

기록마다 JSON과 사진을 내보낼 수 있고 기기 기록만 삭제할 수 있다. 삭제 확인은 서버 기록·이미 내보낸 파일을 삭제하지 않는다. 내보낸 JSON을 다시 가져오는 기능은 이번 범위에 포함하지 않았다.

## 저장과 복구의 경계

브라우저 기록은 해당 기기·브라우저·사이트 주소에 속한다. 다른 주소나 브라우저에서는 공유되지 않는다. 영구 저장을 요청하지만 승인 여부는 브라우저에 달려 있고, 사이트 데이터 삭제 또는 저장소 정리로 사라질 수 있다. 중요한 기록은 내보내거나 서버에 저장한다. 저장 공간 부족 시 결과를 화면에 유지하고 같은 결과의 기기 저장을 다시 시도할 수 있다. [MDN Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API)

서버 저장이 실패하면 서버 전용 `.pending` 초안을 기본 24시간 보존하고 재추론 없는 복구 API를 제공한다. 사진과 초안은 함께 백업한다. 기존 기록이 이후에 바뀌면 예전 복구 결과로 덮어쓰지 않는다. 초안 보관 자체도 실패하면 저장 가능하다고 표시하지 않는다.

농약 사용 조건은 오프라인 묶음에 포함하지 않는다. 서버 이력에서는 당시 병해 안내와 현재 농약 카탈로그를 구분한다. 기기에 설치된 한국어 로컬 음성이 있는 경우 결과 읽기를 제공하고, 없으면 글로 안내한다. 온라인 앱의 음성 모드는 서버 STT·기능 선택·답변 문장을 거친다(`docs/API_SPEC.md`의 `/voice/*`). 오프라인 묶음(`/offline/`)에는 STT·기능 선택 모델이 아직 없어 음성 질문은 오프라인에서 동작하지 않는다(#165~#168). 카메라 실시간 영상 진단은 구현하지 않았다.

## 검증 결과와 실제 기기에서 남은 확인

- ONNX 변환: 동일 입력 텐서 3개, 서버 PyTorch 대비 최대 logit 차이 `1.4007091522216797e-6`, `atol=rtol=1e-4` 통과.
- 실제 Chrome: 모델 준비 → 실제 WASM 추론 → 네트워크 차단 → 새로고침·이력 복원·새 진단 → 서버 저장 성공 후 응답 유실 → 동일 본문 재전송과 중복 없는 저장 확인. 페이지 JS 오류 없음.
- 백엔드 테스트는 별도 임시 DB/사진 폴더에서 실행한다. 운영 기록을 변경하지 않는다.
- Canvas 사진 리사이즈와 서버 Pillow 전처리는 완전히 같은 구현이 아니다. 동일 텐서의 모델 변환 검증을 사진별 전처리 일치나 병해 정확도 검증으로 해석하지 않는다.
- 휴대폰 Chrome/Safari 메모리·처리 시간·저장소 유지, Orange Pi 속도, 실제 농장 사진 정확도와 로컬 음성 가용성은 대상 장치에서 확인해야 한다. 현재 모델은 경량화·양자화하지 않은 약 94MB 모델이다.

기본 테스트 서버는 별도 DB를 설정한 backend `8000`과 Next.js `3100`이다. 테스트의 단색 사진은 실행 흐름 검증용이며 정확도 평가 자료가 아니다.

```powershell
cd frontend
npm run test:offline
node tests/offline-browser.mjs
```

`TEST_ORIGIN` 환경 변수로 테스트 주소를 바꿀 수 있다. 브라우저 통합 테스트는 Chrome과 생성된 모델 파일, 실행 중인 테스트 전용 백엔드가 필요하다. 이 테스트는 헤더 내비로 사진 분석·진단 기록 화면을 오가며, 저장 토스트와 저장 완료 라벨, 동기화 대기·실패 카드도 확인한다.
