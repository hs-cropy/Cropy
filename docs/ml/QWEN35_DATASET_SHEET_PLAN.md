# Cropy Qwen3.5 데이터 시트 구축 계획

최초 작성: 2026-10-06 · 갱신: 2026-10-08 · 대상: 크래파스 팀 내부

## 현재 구축·검수 상태

초기 설명 생성 시트 설계 이후 기능 토큰·handler·TTS 연결을 포함한 v5 데이터 초안이 작성되었다. 7기능 각 400개, 전체 싱글턴 2,800개(train 2,240/개발 validation 560)다. 예시와 보류 멀티턴은 이 집계에서 제외한다.

v6 전체 AI 검수는 문제 미발견 2,239 / 보류 397 / 불합격 164이며 사람 승인 0개다. 형식·분할 검사와 내용 승인, 모델 학습·실행 검증을 구분한다. 실제 tokenizer ID·종료·exporter·handler·TTS·RKLLM 보드 실행은 미검증이다.

[구축 결과](https://github.com/hs-cropy/Cropy/blob/1c52d5c084fb8aca41b7970acc38ca78e6aa1d7f/%EB%A7%88%EC%9D%8Cai/Qwen35_%EB%8D%B0%EC%9D%B4%ED%84%B0%EC%8B%9C%ED%8A%B8/%EC%A0%84%EC%B2%B4%EA%B8%B0%EB%8A%A5400_%EA%B5%AC%EC%B6%95%EA%B2%B0%EA%B3%BC_v5.md)와 [전체 검수 결과](https://github.com/hs-cropy/Cropy/blob/1c52d5c084fb8aca41b7970acc38ca78e6aa1d7f/%EB%A7%88%EC%9D%8Cai/Qwen35_%EB%8D%B0%EC%9D%B4%ED%84%B0%EC%8B%9C%ED%8A%B8/%EC%A0%84%EC%B2%B42800_%EB%A7%A4%EB%89%B4%EC%96%BC%EA%B8%B0%EB%B0%98_AI%EA%B2%80%EC%88%98_v6.md)가 현재 수량·상태의 기준이다. 불합격 수정 → 반환 경계·한국어 TTS·STT 검수 → 사람 승인 → 소량 실행 → 본학습 순서로 진행한다.

아래 1~9절은 최초 설명 생성 설계의 근거·구성·목표량을 보존한 것이다. 120개 점검과 1,000/200/200 목표는 초기 계획이며 현재 기능 토큰 초안 수량이나 승인 완료 수량이 아니다. 모델 ID·revision·변환 지원은 여전히 확정 전이다.

## 1. 제안하는 방향

**Qwen3.5가 CNN 진단 결과와 제공된 병해·농약 정보를 이해하기 쉬운 한국어로 설명하도록, 근거가 포함된 대화 데이터 시트를 만든다.** 먼저 120개 대화로 작성 기준과 모델 입력 형식을 점검하고, 이후 학습 1,000개·개발 검증 200개·최종 평가 200개로 확대한다. 수량과 일정은 이 프로젝트의 제안이며 강의의 필수 조건이나 성능 보장치가 아니다.

기존 [LLM 적용 계획](LLM_FINETUNING_PLAN.md)의 역할을 유지하면서, 마음AI 자료의 기능 정의·발화 다양화·별도 평가 원칙을 실제 작성 가능한 시트 구조로 구체화한다. 이번 문서는 데이터 시트의 설계이며, 검수된 학습 데이터나 Qwen 학습·보드 구동을 완료했다는 기록이 아니다.

| 구분 | 이번 계획 |
|---|---|
| 사용자 | 고추·무·배추를 재배하며 짧은 한국어 또는 음성으로 질문하는 사용자 |
| 1차 입력 | 백엔드가 제공한 진단·근거 JSON, 사용자 질문, 필요한 이전 대화 |
| 1차 출력 | 후보 설명, 제공된 관리 정보 안내, 확인 질문, 재촬영 안내, 정보 부족 안내 |
| 기본 답변 스타일 | 쉬운 한국어 2~4문장, 필요한 안내부터 전달. 중요한 조건을 생략하면서 길이를 줄이지 않음 |
| 모델 | Qwen3.5 사용 예정. 세부 크기는 미확정이며 기존 문서의 `Qwen/Qwen3.5-2B`를 우선 검증 후보로 둠 |
| 실행 환경 | 기존 계획의 Orange Pi 5 Plus/RK3588을 우선 가정. 모델·변환 도구·런타임 호환 확인 필요 |
| 후속 확장 | 실제 이미지 입력, 촬영·이력 조회 등 도구 호출은 별도 데이터 버전에서 검토 |

Qwen3.5-2B 공식 모델은 비전 인코더를 포함한다. 다만 현재 서비스의 CNN과 백엔드 구조를 활용하는 첫 단계에서는 텍스트 근거를 입력한다. 사진을 직접 읽게 하려면 이미지·설명 정답·이미지 처리 설정과 별도의 평가가 필요하다. [Q1]

| 특강2 p22~25: train에서 다양한 calibration 발화 선택 | 학습 데이터 중 300개를 표시하고 실제 변환 도구 형식에 맞춰 변환 |

### 예제 데이터 시트에서 가져올 구조

HomeIoT와 Jeju의 학습 시트는 주로 **번호 / 기능명 / LLM Output / 질문**의 4열이며, LLM Output에는 기능별 호출 토큰이 들어 있다. 기능별 분류와 발화 다양화에 참고할 수 있다. 그러나 Cropy가 필요한 **진단 근거와 자연어 정답 응답**은 별도로 작성해야 한다. 함수 호출 문자열만을 설명형 모델의 정답으로 사용하지 않는다. [X1, X2]

두 워크북에는 숨김 시트와 이전 버전도 있어 모든 시트의 행을 합쳐 데이터량으로 계산하면 안 된다. 사용할 버전과 행 범위를 먼저 지정한다. HomeIoT의 멀티턴 기획은 참고하되, 실제 학습 행 하나에 완결된 이전 대화가 들어 있다고 가정하지 않는다.

확인한 주요 시트와 범위는 다음과 같다. 27개 시트 전체를 읽었으며 아래는 계획에 직접 사용한 부분이다. 행 수는 참고자료의 규모이고 Cropy의 구축 목표량은 아니다.

| 워크북 / 시트 | 확인 범위 | 참고할 구조 |
|---|---|---|
| HomeIoT / `AI_Expo_2025Function Descriptio` | `A1:M36` | 기능 정의, 출력 규약, 필요한 인자 부족 시 확인 질문 |
| HomeIoT / `1차 싱글턴 KOR - train` | `A1:D5748` | 헤더 제외 5,747개 질문·함수 출력 행 |
| HomeIoT / `1차 싱글턴 - eval` | `A1:E111` | 헤더 제외 110개 평가 행 |
| Jeju / `기획 시트` | `B1:AA48` | 구현 여부, 세부 조건, 함수·인자, 예상 질답, 키워드·어투·생성 지시 |
| Jeju / `2-1차 train data` | `A1:D4802` | 헤더 제외 4,801개 질문·함수 출력 행 |
| Jeju / `2-1차 eval data` | `A1:D211` | 헤더 제외 210개 평가 행 |

**검수에 반영할 실제 사례:** HomeIoT 최신 학습에는 제품 QA 864행이 있지만 해당 평가 시트에는 제품 QA 기능이 없다. 기능 정의 시트 `F34:I35`는 냉장고인데 `L34:L35` 질문은 블라인드로 남아 있다. Jeju 기획 시트의 `J14:M14`에는 `line/lines`, `J22:M22`에는 `weekday/holiday` 인자 불일치가 있다. 이를 참고해 Cropy에서는 기능별 학습·평가 커버리지, 질문·근거·정답의 의미 일치, 필드명·인자 일치를 함께 검수한다.

### 그대로 옮기지 않을 규칙

- `<maum_...>`, `<jeju_...>` 등의 전용 토큰은 해당 예제의 실행 규약이다. Qwen에는 확정한 모델의 대화 템플릿을 적용한다.
- 특강1의 문장부호·한글 외 문자 제거는 HomeIoT 발화 작성 예시다. Cropy에서는 숫자, 소수점, 날짜, 단위, JSON 문장부호를 보존한다.
- 특강1·3의 QCS6490/Qualcomm 환경과 특강2의 RK3588/RKLLM 환경을 구분한다. 강의의 다른 모델 속도나 양자화 설정을 Qwen3.5 실측값으로 쓰지 않는다.
- 기능별 400문장·평가 20문장은 강의 예시량이다. 우리 데이터는 기능 수보다 실제 오류 유형과 검수 가능 범위로 규모를 결정한다.

## 3. 구축할 엑셀의 구성

초기 제안 파일명은 `Cropy_Qwen35_데이터시트_v1.xlsx`이며 아래 6개 시트 표는 최초 설명 생성 설계다. 현재 기능 토큰·TTS·검수 시트의 실제 구성은 위 v5/v6 결과와 원본 워크북을 따른다.

| 시트 | 작성 단위 | 핵심 열 |
|---|---|---|
| `00_작성규칙` | 설정·규칙 한 항목 | 데이터 버전, system 문구·버전, 모델 후보/확정 ID·revision, 템플릿 revision, thinking 설정, 작성·검수 기준 |
| `01_기능정의` | 기능 한 개 | `scenario_type`, 기능 설명, 필요한 입력, 기대 행동, 답변에 포함할 내용, 금지 내용, 대표 질문 |
| `02_근거컨텍스트` | 근거 묶음 한 개 | `context_id`, `context_json`, `source_ref`, `source_version`, `verified_at`, `evidence_status`, `origin_type` |
| `03_대화데이터` | 사용자 질문·정답 응답 한 턴 | `conversation_id`, `turn_index`, `scenario_type`, `context_id`, `user_text`, `assistant_text`, `expected_action`, `evidence_fields`, `variation_tags` |
| `04_검수분할` | 대화 한 개 | `conversation_id`, `scenario_group_id`, `seed_id`, `split`, 작성자, 검수자, `review_status`, 오류 사유, `calibration_selected` |
| `05_평가결과` | 모델 실행·대화·턴별 결과 | `run_id`, `conversation_id`, `turn_index`, 실제 응답, 근거 준수, 기대 행동, 한국어 품질, 오류 태그, 지연, 평가자 |

**대화 한 개가 수량 집계의 기본 단위다.** 3턴 대화는 `03_대화데이터`에서 3행이지만 학습량은 1개 대화로 센다. `turn_index`는 1부터 순서대로 부여한다. 데이터 시트의 자연어 정답은 한 가지 표현을 보여주는 예시이며, 모델 평가는 문장 완전 일치보다 근거와 행동의 일치를 본다.

`origin_type`은 `api_snapshot / human_scenario / synthetic` 등으로 구분한다. 합성 시나리오는 실제 진단 기록으로 집계하지 않는다. `evidence_status`는 사실 근거의 검증 상태이고, `review_status`는 대화의 작성·검수 상태이므로 둘을 구분한다. 정답이 “정보가 없다”인 사례는 근거가 부족하더라도 올바른 대화로 승인할 수 있다.

`source_ref`에는 문서명·URL·절/쪽수 또는 비식별 API 스냅샷 ID를 기록한다. 원문을 외부 생성형 서비스에 업로드해 증량하지 않고, 팀 내부에서 허용된 자료와 범위로 작성한다.

### 현재 API에서 가져올 컨텍스트

현재 [진단 응답 스키마](../../backend/app/schemas/diagnosis.py)를 기준으로 다음 필드를 사용한다. 단순히 병명과 점수만 옮기지 않는다.

| 필드 | 작성·검수 기준 |
|---|---|
| `disease_name`, `category`, `top_predictions` | 모델의 후보로 설명. 확진 정답으로 표현하지 않음 |
| `confidence` | 분류 점수. 실제 발병 확률이나 신뢰구간으로 해석하지 않음 |
| `selected_crop`, `predicted_crop`, `crop_mismatch` | 사용자가 선택한 작물과 예측 작물이 다르면 확인하는 사례 작성 |
| `prediction_mode`, `model_version`, `preprocessing_version` | 실제 모델·mock·이전 기록을 구분하고 근거 버전 추적 |
| `recapture.region/instruction/candidates` | 백엔드가 제공한 안내를 전달. LLM이 재촬영 조건이나 후보를 임의로 변경하지 않음 |
| `description`, `causes`, `prevention` | 현재 수기 시드도 있으므로 출처를 검토해 사용할 내용만 승인 |
| `pesticides[].source/verification_status/synced_at` | 작물·병해별 등록정보의 검증 상태와 조회 시점 보존 |
| `pesticides[].dilution/usage/safety` | 값이 없거나 미검증이면 추측하지 않음. 이름만 있다고 사용 조건까지 확인된 것은 아님 |

현재 `model_loaded`는 진단 응답이 아닌 상태 응답에 있다. 별도 상태 입력이 필요하면 입력 구성기에 명시적으로 추가한다. 시트 관리용 `evidence_status`·`source_ref`도 기존 API 필드라고 가정하지 않는다. `severity`는 현재 DB의 병해 속성이므로 사진에서 측정한 진행 정도로 설명하지 않는다.

모델 미로드·mock처럼 앱에서 먼저 차단할 상황은 통합 평가 사례로 기록한다. 실제 서비스에서 LLM을 호출하지 않는 사례는 LLM 학습 1,000개에 억지로 포함하지 않는다.

## 4. 시나리오와 목표 수량

기존 계획의 1,000개 학습 목표를 유지한다. 아래 범주는 대화별 주 시나리오로 한 번만 집계한다.

| 주 시나리오 | 학습 목표 | 포함할 상황 |
|---|---:|---|
| 병해 결과 설명 | 200 | 6개 질병, 후보 설명, 점수 질문, 병명 단정 요구 |
| 정상 분류 설명 | 100 | 정상 3종, 낮은 점수, 사용자가 증상을 계속 호소하는 경우 |
| 재촬영 안내 | 150 | 제공된 촬영 지침, 다시 찍는 이유, 재촬영 전후의 컨텍스트 변화 |
| 원인·예방·관리 질문 | 150 | 검수된 제공 정보 설명, 정보 누락, 다른 작물의 정보 혼동 |
| 농약 정보·정보 부족 | 150 | 검증된 조회 결과, 미검증/누락 필드, 농약 여러 개, 수치 추측 요구 |
| 후속 질문·대상 확인·STT 오류 | 150 | “그 병/그 약”, 작물명 수정, 이전 진단 지시, 의미가 모호한 오인식 |
| 지원 범위·입력 충돌·지시 우회 | 100 | 미지원 작물, 선택/예측 작물 불일치, 컨텍스트 안의 명령, 확진 강요 |
| **합계** | **1,000** | **승인된 대화 기준** |

별도로 개발 검증 200개와 최종 평가 200개를 만든다. 정상 이미지가 많다는 이유로 정상 대화 비중을 CNN 이미지 분포대로 늘리지 않는다. 무노균병·무검은무늬병 혼동은 설명·재촬영·확인 질문에 걸쳐 충분히 포함하되, 두 질병만으로 다른 범주를 대체하지 않는다.

초기 분포 목표는 다중 턴 30% 이상, STT/띄어쓰기 변형 10~15%, 누락·불일치·불확실성 상황 20% 이상으로 제안한다. 이들은 **서로 겹칠 수 있는 태그 비율**이며 1,000개에 별도로 더하는 수량이 아니다. STT 실제 로그가 없으면 합성 변형으로 표시하며, 이를 실제 음성 인식 성능으로 보고하지 않는다.

## 5. 수집·작성·검수 절차

1. **기능과 근거를 고정한다.** 현재 API 응답과 병해 설명·농약 조회 자료에서 필요한 필드를 정리한다. 사용 조건이 검증된 농약 데이터가 부족하면 이를 꾸며 채우지 않고 ‘정보 부족’ 사례와 근거 확보 작업으로 남긴다.
2. **시나리오 그룹을 먼저 만든다.** 같은 진단/사진, 재촬영 전후 묶음, 동일 시드 질문의 표현 변형, 같은 대화의 모든 턴을 하나의 그룹으로 연결한다. 여러 관계가 이어지면 연결된 전체 묶음을 같은 분할에 둔다.
3. **그룹을 나눈 뒤 발화를 다양화한다.** `scenario_group_id` 단위로 train/validation/test를 지정하고 이후 변형도 같은 분할을 상속한다. 행을 무작위로 섞어 분할하지 않는다.
4. **정답 행동부터 정한다.** `answer / ask_clarification / recapture_guidance / insufficient_information / unsupported_scope` 중 해당 행동을 적고, 이를 뒷받침하는 JSON 필드 경로를 `evidence_fields`에 기재한다.
5. **사용자 발화와 정답을 작성한다.** 단순 병명 치환 외에 정보 누락, 여러 후보, 작물 수정, 이전 발화 지시를 조합한다. 문장 의미를 알아낼 수 없는 STT 오류는 확인 질문이 정답이다.
6. **작성자 외 팀원이 검수한다.** `draft → reviewed → approved` 또는 `rejected` 상태로 관리한다. 농약 조건·근거 충돌은 백엔드 담당과 함께 확인하고 이견이 해결되지 않으면 내보내지 않는다.
7. **승인된 대화만 내보낸다.** 대화 전체가 승인되고 필수값·그룹·근거가 유효한 경우에만 JSONL로 변환한다. 모델에는 필요한 근거·질문·이력·정답만 전달하고 검수용 메타데이터는 별도로 보관한다.

### 중요한 검수 기준

- CNN의 예측 클래스와 실제 정답 라벨을 구분한다. 정답 라벨을 아는 평가 사례도 LLM 입력에 숨겨 넣어 맞히게 하지 않는다. 설명 모델은 제공된 결과를 ‘후보’로 전달하며, CNN 오류를 문장 학습만으로 수정했다고 평가하지 않는다.
- `null`, 빈 목록, 정보 없음과 숫자 0을 구분한다. 농약 조건은 현재 서비스의 `source=PSIS`, `verification_status=verified`, `synced_at` 존재 조건과 실제 대상 작물·병해 일치를 검토한다. 동기화 시점만으로 현재 등록 상태가 항상 유효하다고 단정하지 않는다.
- `recapture=null`은 확진 또는 촬영이 충분하다는 증거가 아니다. 특히 재촬영 후 값이 비는 현재 API 동작을 고려한다.
- 다중 턴 중 진단이 바뀌면 해당 턴의 `context_id`도 바꾼다. 정답을 만들 때 모델에게 제공되지 않는 미래 턴이나 다른 진단 정보를 사용하지 않는다.
- 같은 질문·같은 근거인데 정답 행동이 다른 행, 근거 없는 병명·농약 수치, 임의의 심각도 판정은 반려한다.
- 모델 정답에는 `<think>` 내부 추론이나 마음AI 전용 호출 토큰을 수작업으로 넣지 않는다.

## 7. Qwen3.5에 맞춘 내보내기와 평가

### 대화 형식

`03_대화데이터`의 같은 `conversation_id`를 턴 순서대로 묶어 `system → user → assistant → user → assistant` 형태의 `messages`로 내보낸다. 각 user 입력에는 해당 시점에 유효한 컨텍스트와 질문을 일관된 형식으로 넣는다. 학습·평가·서비스에서 같은 입력 구성기를 사용하도록 계획한다.

첫 출력 예시는 다음과 같다. 이는 내부 정규화 예시이며 특정 학습 도구에서 추가 설정 없이 동작한다는 의미가 아니다.

```json
{"messages":[{"role":"system","content":"제공된 근거에 따라 짧고 쉬운 한국어로 답한다. 진단 후보를 확진으로 표현하지 않고, 없는 정보는 추측하지 않는다."},{"role":"user","content":"context: {\"pesticides\":[]}\n질문: 사용할 약이 뭐야?"},{"role":"assistant","content":"현재 제공된 정보에는 확인된 농약 목록이 없어 안내하기 어렵습니다."}]}
```

실제 system 문구는 작성 규칙 시트에서 버전 관리하며 예시보다 상세한 재촬영·작물 불일치·근거 처리 기준을 포함한다. `expected_action`, 검수자, 정답 라벨, split 등 정답을 노출하거나 추론에 불필요한 열은 모델 입력에서 제외한다.

Qwen3.5-2B 공식 모델카드는 기본 non-thinking 동작을 명시한다. 다른 크기의 기본값까지 같다고 가정하지 않고, 우리 설명형 실험은 `enable_thinking=False`를 명시하는 방안을 우선 검증한다. `/think`·`/nothink` 같은 발화를 데이터 규칙으로 사용하지 않는다. 직렬화는 고정한 모델의 processor/tokenizer와 chat template에 맡긴다. [Q1, Q2]

학습 프레임워크가 요구하는 메시지·이미지·마스킹 규격은 선택 후 확인한다. assistant 정답만 학습 대상이 되는지, 종료 토큰이 들어가는지, user/근거/정답이 잘리지 않는지 20~50개로 먼저 확인한다. 2,048 토큰을 초기 예산 후보로 두되 실제 길이 분포와 배포 한도로 정하며 중요한 근거와 정답을 조용히 잘라내지 않는다.

### 평가 및 다음 단계 진입 기준

- 파일럿은 **120개 대화: 학습 후보 100개 + 개발 검증 20개**로 시작한다. 이후 목표 1,000/200/200에 포함하는 수량이며 추가 120개가 아니다. 개발 검증 20개는 형식·실패 유형 점검용으로 사용한다.
- 기본 Qwen + 같은 프롬프트로 먼저 개발 검증 결과를 기록한다. 반복 실패가 남으면 소규모 미세조정으로 효과를 비교한다. 데이터를 만들었다는 이유만으로 학습을 필수화하지 않는다.
- 확대 단계에서 별도 그룹으로 최종 평가 200개를 동결한다. 프롬프트·모델 선택은 개발 검증 200개로 수행한다. 최종 평가를 보고 수정에 활용한 사례는 개발 자료로 전환하고 새 최종 평가 그룹을 확보한다.
- 근거 준수·기대 행동·관련성·한국어 간결성을 항목별로 평가한다. 점수는 0=실패, 1=부분 충족, 2=충족으로 두고, 근거 없는 농약 수치·확진·재촬영 무시는 별도 중대 오류로 기록한다.
- 초기 채택 기준은 최종 평가에서 중대 오류 0건, 목표 실패 유형이 기본 모델보다 감소, 나머지 시나리오의 뚜렷한 악화 없음으로 제안한다. 유한한 평가에서 0건이라는 결과는 실제 서비스의 무오류 보장이 아니다.
- JSON 파싱·대화 순서·필수값·승인 상태는 내보내기 대상 전부 통과해야 하고, 그룹 분할 중복은 0건이어야 한다. 길이 초과는 수정 또는 명시적인 제외 대상으로 기록한다.
- 7개 주 시나리오 각각이 train/validation/test에 포함되는지 교차표로 확인한다. 또한 질병 6종·정상 3종, 무 질병 혼동, 정보 누락, 작물 불일치, 다중 턴의 태그별 평가 누락을 점검한다. 시나리오별 통과율과 전체 통과율을 함께 보고한다.
- 보드 배포 시 학습 데이터에서 300개 입력을 고르게 골라 calibration용으로 표시한다. validation/test는 사용하지 않으며, 이를 별도 학습 300개로 더해 세지 않는다. 변환 도구의 생성 target도 종료·형식·내용을 점검한다.
- 실제 모델 ID/revision·템플릿·도구 버전을 고정하고, 기본/미세조정 및 양자화 전/후를 같은 조건으로 비교한다. 보드 실측 전에는 변환 성공·속도·메모리 충족을 완료로 표시하지 않는다.

## 8. 착수 후 실행 순서와 역할 제안

다음은 팀 5명의 기존 담당 범위를 활용한 **10작업일 초안**이다. 아직 합의된 배정이나 완료 실적은 아니다. 검수 시간이 부족하면 수량을 낮추고 승인 기준은 유지한다.

| 기간 | 작업 | 담당 제안 | 완료 기준 |
|---|---|---|---|
| 1~2일 | 모델 후보·실행 환경, 기능 정의, 컨텍스트 계약, 시트 양식 확정 | 김헌영 + 박성호 + 이서하 | 필수 열·행동 기준과 실제 API 매핑 확인 |
| 3~4일 | 파일럿 120개 작성, 교차 검수, 20~50개 내보내기 점검 | 김헌영 중심, 담당별 검수 | 승인된 파일럿과 수정할 오류 목록 확보 |
| 5일 | 기본 Qwen 개발 평가, 답변·STT 실패 유형 분석 | 김헌영 + 고명준 + 김민서 | 모델 응답·근거·화면/음성 평가 기록 |
| 6~8일 | 그룹 분할 고정, 1,000/200/200 목표로 확대 | 기능별 분담, 작성자 외 교차 검수 | 수량뿐 아니라 근거·변형·대화 다양성 충족 |
| 9일 | 중복·모순·누락·길이 검수, 평가셋 동결 | 김헌영 + 박성호 | 반려 행 제외, 그룹 누출 없음 |
| 10일 | 버전 배포, calibration 후보 300개 표시, 후속 학습 여부 결정 | 김헌영 + 이서하 | 시트·JSONL·분할·검수 요약·설정 manifest 확보 |

박성호는 API/농약 근거 조건, 고명준은 실제 STT 발화와 음성 전달, 김민서는 화면·재촬영 안내의 일치, 이서하는 모델·런타임 호환, 김헌영은 시나리오·분할·검수 기준·평가를 중심으로 맡는 안이다. 모델 호환성 확인이 길어져도 모델에 독립적인 시트 작성은 진행할 수 있다.

첫 산출물은 **엑셀 빈 양식 + 대표 시나리오 + 검수 기준**, 다음 산출물은 **승인된 파일럿 120개**다. 대규모 미세조정 전에 데이터 형식, 근거 준수, 기본 모델의 실제 실패를 먼저 확인한다.
