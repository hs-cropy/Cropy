# cropy · 약 10분 발표 대본

총 배정 시간: 600초. 실제 속도에 맞춰 리허설로 조정하세요.

## 1. 표지 (20초)

안녕하세요. 크래파스 팀입니다. 저희가 만들고 있는 cropy는 작물 사진으로 병해를 확인하고, 다음에 무엇을 해야 하는지 쉽게 안내하는 서비스입니다. 오늘은 현재 구현한 웹앱에서 출발해, 오프라인 음성 단말로 확장하는 계획을 말씀드리겠습니다.

근거: 프로젝트 개요와 2026-09-17 이전 백로그 기준. 사진: 로컬 AI Hub 노지 작물 질병 진단 데이터의 고추 정상 예시. 현장 시연 사진 아님.

## 2. 문제 정의 (50초)

저희는 병명을 출력하는 것만으로 사용자의 문제가 끝나지는 않는다고 보았습니다. 첫 번째는 사진의 한계입니다. 비슷한 증상은 처음 찍은 사진에 구분 단서가 충분하지 않을 수 있습니다. 그때 사용자는 다시 찍어야 하는지, 어디를 찍어야 하는지 알기 어렵습니다. 두 번째는 사용 방식입니다. 작업 중에 긴 설명이나 복잡한 화면을 읽는 부담을 줄여야 합니다. 그래서 큰 글씨와 단순한 버튼, 짧은 음성 안내를 함께 설계합니다. 세 번째는 통신입니다. 인터넷이 끊긴 상황에서도 핵심 기능이 유지되도록 단말 안에서 처리하는 방향을 잡았습니다. 이 세 가지는 앞으로 사용자와 현장 검증으로 확인할 설계 가설입니다.

근거: docs/project/12_프로젝트_개요_양식.md. 문제는 설계 배경으로 제시하며 사용자 조사로 입증했다고 주장하지 않음.

## 3. 사용자와 범위 (45초)

예를 들어 무를 키우는 사용자가 잎의 반점을 발견한 상황입니다. cropy에서 사진을 찍으면 진단 후보와 관련 정보를 확인합니다. 추가 단서가 필요하면 안내에 따라 부위를 바꿔 찍고, 결과와 대응 정보를 다시 살펴봅니다. 현재 분류 범위는 고추, 무, 배추 세 작물입니다. 각 작물의 병해 두 종류와 정상 상태를 합쳐 아홉 개 클래스로 제한했습니다. 모든 작물이나 모든 병을 진단하는 범용 서비스로 설명하지 않겠습니다. 화면 중심의 웹앱으로 흐름을 먼저 검증하고, 같은 흐름을 음성으로 사용할 수 있도록 확장할 계획입니다.

근거: docs/ml/MODEL_SPEC.md; docs/ml/LLM_FINETUNING_PLAN.md. 사진: 로컬 AI Hub 데이터 무 정상 예시, 사용자 인터뷰나 실제 서비스 시연을 의미하지 않음.

## 4. 현재 앱 화면 (60초)

왼쪽은 현재 프로젝트를 실행해서 캡처한 실제 화면입니다. 앱의 밝은 아이보리 배경과 갈색 글자, 노란색 주요 버튼을 발표 자료에도 가져왔습니다. 첫 화면에서는 사진을 촬영하거나 파일을 올리고, 작물을 선택할 수 있습니다. 큰 글씨 전환도 제공해 읽기 부담을 줄이도록 했습니다. 두 번째 화면은 데이터셋의 고추 사진을 업로드한 상태입니다. 여기서 보여드리는 것은 화면과 업로드 동작이며, 오늘 캡처 자체가 새로운 진단 정확도 검증을 뜻하지는 않습니다. 프로젝트에는 진단과 재촬영, 이력 조회를 연결하는 코드가 구현되어 있습니다. 다음 단계에서는 이 흐름이 실제 모델을 불러온 보드 환경에서도 유지되는지를 확인하고, 음성 입출력을 연결합니다.

근거: 실제 로컬 Next.js 화면 캡처, 2026-09-17. frontend/src/components/DiagnoseForm.tsx; docs/project/BACKLOG.md. 이미지 내 문구는 기존 앱 그대로.

## 5. 재촬영 (60초)

cropy의 중요한 차별점은 결과가 애매할 때 다음 촬영 행동을 제안한다는 점입니다. 처음 사진에서 비슷한 병해 후보가 나오면, 구분에 도움이 되는 부위를 안내하는 흐름을 둡니다. 화면의 문장은 그 경험을 보여 주는 예시입니다. 사용자가 안내에 따라 다시 촬영하면 처음 결과와 함께 재확인하고 이력에 남깁니다. 다만 재촬영 기능이 구현되었다는 것과 정확도가 실제로 개선되었다는 것은 구분해야 합니다. 같은 평가 사례에서 한 장만 사용했을 때와 재촬영을 했을 때를 비교해 효과를 확인할 예정입니다. 촬영 횟수가 늘어나는 부담도 함께 살펴봐야 합니다. 이번 발표에서는 사용자 흐름에 집중하고 내부 판단 조건이나 수치 등 세부 알고리즘은 공개하지 않습니다.

근거: docs/project/BACKLOG.md; docs/operations/ORANGEPI5_MIGRATION_BACKLOG.md; docs/project/10_팀_프로젝트_규칙.md. 안내 문구는 UX 예시. 재촬영 임계값·통합 가중치 비공개.

## 6. 현재 상태 (50초)

현재 확보한 기반은 사진을 분류하는 모델과 웹 서비스 흐름입니다. ResNet50을 사용한 아홉 클래스 분류, 진단과 재촬영 및 이력 API, 모바일 화면, 학습과 평가 코드가 있습니다. 하지만 PC의 구현이나 기록을 보드의 완료 상태로 바꾸어 말하지는 않겠습니다. 오른쪽은 앞으로 실제 장치에서 확인할 작업입니다. ARM64 환경에서 의존성을 설치하고 실제 모델을 로드해야 하며, 사진 진단과 재촬영까지 성공해야 합니다. 이후 언어 모델과 음성을 붙이고, 인터넷 차단과 재부팅 상황을 검증합니다. 특히 API가 정상 상태 코드를 반환하는 것만으로는 충분하지 않습니다. 실제 가중치가 로드된 상태에서 기대한 기능이 동작한다는 증거를 남기겠습니다.

근거: docs/project/BACKLOG.md; docs/operations/ORANGEPI5_MIGRATION_BACKLOG.md OP-03~16. 보드 항목은 모두 미검증 계획.

## 7. 기술 구조 (65초)

전체 구조의 중심은 기존 진단 서비스입니다. 사진을 CNN이 분류하면 백엔드는 병해와 관련 정보를 조회하고, 결과를 JSON 형태로 관리합니다. 웹 화면과 이력은 이 결과를 사용합니다. 아래쪽은 추가할 음성 경로입니다. 사용자의 말을 STT로 텍스트로 바꾸고, Qwen에 질문과 진단 결과, 확인된 데이터베이스 정보를 함께 전달합니다. Qwen의 역할은 그 근거를 이해하기 쉬운 한국어로 설명하는 것입니다. 사진을 보지 않은 언어 모델이 병을 새로 판단하거나 농약 수치를 기억으로 채우게 하지 않습니다. 생성된 내용은 근거와 수치를 확인한 뒤 음성으로 읽습니다. 타임아웃이나 모델 실패가 발생하면 기존 진단 결과와 템플릿 안내를 유지합니다. 목표 장치는 Orange Pi 5 Plus 16기가바이트이며, 우선 CNN은 CPU, 언어 모델은 RKLLM을 통한 NPU 실행으로 검증합니다.

근거: docs/ml/LLM_FINETUNING_PLAN.md §3~4; docs/operations/ORANGEPI5_DEPLOY.md. Qwen과 STT/TTS 경로는 계획. DB 시드 정보의 검증 여부를 별도 확인해야 함.

## 8. 이전 순서 (60초)

장치 이전은 다섯 단계로 진행합니다. 첫째, 기존 CNN을 CPU로 실행하고 실제 사진 진단과 재촬영, 이력을 확인합니다. 여기에서 정확도와 응답 시간의 기준선을 확보합니다. 둘째, 제공받는 RKLLM 패키지와 드라이버 조합을 확인하고 언어 모델을 연결합니다. Qwen3.5-2B를 첫 후보로 삼지만, 사용할 리비전과 변환 가능 여부는 수령한 도구로 확인한 뒤 확정합니다. 셋째, 오프라인 음성 입력과 출력을 각각 확인하고 전체 흐름에 붙입니다. 넷째, 모든 구성 요소를 함께 올린 상태에서 속도와 메모리, 온도를 측정합니다. 마지막으로 목표를 못 맞추는 부분을 최적화합니다. CPU로 목표를 만족하면 유지하고, 필요할 때 ONNX나 RKNN을 비교합니다. 이 순서로 기능 문제와 성능 문제를 구분하겠습니다.

근거: docs/operations/ORANGEPI5_MIGRATION_BACKLOG.md OP-04~20; docs/ml/LLM_FINETUNING_PLAN.md §4. Qwen3.5-2B 호환성은 확인 전.

## 9. 사투리와 파인튜닝 (50초)

사투리 입력을 잘 이해할지는 모델 이름만으로 판단하기 어렵습니다. 그래서 같은 질문을 두 경로로 평가합니다. A는 사람이 정확하게 받아쓴 문장을 Qwen에 직접 넣는 방식입니다. 여기에서는 사투리 표현 자체를 이해하는지와 근거를 지키는지를 봅니다. B는 실제 음성을 STT에 통과시킨 결과를 넣는 방식입니다. A에서는 성공하고 B에서 실패한다면 음성 인식 단계의 문제를 먼저 봐야 합니다. 병명이나 농약 이름, 숫자를 잘못 알아들은 경우에는 임의로 고치지 않고 확인하도록 설계합니다. 기본 모델과 프롬프트로 해결되지 않는 실패가 반복될 때에만 데이터를 만들어 LoRA를 검토하고, 학습 전후와 변환 후 결과를 비교하겠습니다.

근거: docs/ml/LLM_FINETUNING_PLAN.md. 평가 설계이며 사투리 성능·학습 효과를 입증한 결과가 아님.

## 10. 검증 기준 (50초)

완료 기준은 네 가지로 정리했습니다. 기능 측면에서는 실제 모델이 로드된 상태에서 진단, 재촬영, 이력이 성공해야 합니다. 성능은 첫 로드와 예열 후를 구분하고 중앙값뿐 아니라 느린 응답을 보여 주는 p95도 기록합니다. CNN 단건 일 초 이내는 전처리를 포함한 초기 목표이며, 아직 보드에서 측정한 수치가 아닙니다. 통합 후에는 서른 회 진단과 삼십 분 반복 운용으로 메모리와 온도, 오류를 함께 확인합니다. 마지막으로 인터넷을 차단하고 재부팅해도 자동 실행과 데이터 보존이 되는지 봅니다. 음성을 포함한 전체 응답 시간 목표는 CPU 기준선을 얻은 뒤 팀에서 확정하고 근거를 남길 계획입니다.

근거: docs/operations/ORANGEPI5_MIGRATION_BACKLOG.md OP-04,05,15,16. 초기 CNN 목표 1초. 전체 음성 지연 목표는 이후 확정.

## 11. 역할과 일정 (60초)

팀은 다섯 명이 역할을 나누되, 연결 구간의 완료 증거를 함께 확인합니다. 김헌영은 PM과 모델 및 데이터 평가를 맡고, 김민서는 모바일 화면과 접근성을 담당합니다. 박성호는 API와 데이터베이스, 언어 모델에 전달할 입력 계약과 실패 응답을 맡습니다. 고명준은 카메라와 음성 입출력, 이서하는 ARM64 배포와 복구 및 자원 측정을 담당합니다. 학기 초반에는 웹과 모델 기준선, 입력 규격을 정리합니다. 중반에는 보드와 Qwen, 음성 경로를 연결하고, 후반에는 전체 성능과 안정성을 측정해 필요한 개선을 합니다. 단, 보드 도착이 빠르면 정해진 배포 주차를 기다리지 않고 즉시 검증합니다. 장비가 늦어지면 PC에서 준비할 수 있는 데이터와 계약 작업을 진행하고, 보드 미검증 상태를 분리해 기록합니다.

근거: docs/operations/ORANGEPI5_MIGRATION_BACKLOG.md 역할·게이트; docs/project/08_스프린트_백로그.md. 일정은 게이트 중심 요약이며 실제 완료 상태를 나타내지 않음.

## 12. 마무리 (30초)

cropy는 사진 한 장의 결과를 보여 주는 데서 나아가, 필요할 때 무엇을 다시 확인해야 하는지 안내하는 서비스를 목표로 합니다. 현재 웹과 진단 흐름을 기반으로, CPU 기준선부터 Qwen과 음성, 전체 측정의 순서로 확장하겠습니다. 다음으로 확인할 가장 구체적인 결과는 Orange Pi 5 Plus에서의 실제 진단과 CPU 성능 기준선입니다. 크래파스 팀의 cropy였습니다. 감사합니다.

근거: 본 발표의 계획 및 현재 상태 요약.
