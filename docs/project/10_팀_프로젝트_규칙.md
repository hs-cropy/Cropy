# 크래파스 팀 프로젝트 규칙

> 저장소: https://github.com/hs-cropy/Cropy
> 대상: 팀원 5명 전원. 규칙 변경은 팀장 승인 후 이 문서를 먼저 고치고 적용한다.

## 1. 역할과 폴더 소유권

| 파트 | 담당 | 소유 폴더 |
|---|---|---|
| PM · 모델 | 김헌영 | `ml/`, `docs/` |
| 프론트엔드 | 김민서 | `frontend/` |
| 백엔드 (API) | 박성호 | `backend/app/` |
| 카메라 · 음성 | 고명준 | `frontend/src/features/camera/`, `frontend/src/features/voice/` |
| 백엔드 (배포) · 디바이스 | 이서하 | `backend/Dockerfile`, `backend/scripts/`, `device/`, `docker-compose.yml`, `.github/` |

- 자기 폴더 밖을 고쳐야 하면 해당 소유자에게 먼저 말하고, PR 리뷰어로 지정한다.
- 여러 파트에 걸친 변경(API 계약 등)은 관련 담당자 전원이 리뷰한다.
- 오렌지파이 도착 전까지 인프라 담당은 백엔드 파트와 함께 움직인다.

## 2. 브랜치

- `main`은 항상 실행 가능한 상태를 유지한다. 직접 푸시 금지, PR로만 병합한다.
- 작업 브랜치 이름: `<파트>/<짧은-설명>`
  - 예: `fe/history-pagination`, `be/history-crop-filter`, `ml/onnx-export`, `cam/live-preview`, `inf/ci-workflow`, `docs/week3-report`
- 브랜치는 하나의 작업 단위만 담는다. 끝나면 병합 후 삭제한다.
- 병합 방식은 **Squash and merge**. 커밋 제목이 곧 변경 이력이 되므로 PR 제목을 커밋 규칙에 맞춰 쓴다.

## 3. 커밋 메시지

형식: `태그: 내용` (한국어, 한 줄 요약, 마침표 없음)

| 태그 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 설정, 의존성, 빌드 |
| `ml` | 모델·데이터셋·학습 스크립트 |

- 예: `feat: 이력 목록 무한 스크롤`, `fix: 정상 작물 진단 시 심각도 배너 숨김`, `ml: ONNX export 스크립트`
- 작성자는 본인 GitHub 계정으로만 남긴다. 도구 자동 서명(Co-Authored-By 등)은 넣지 않는다.
- 학습된 체크포인트(`*.pth`, `*.onnx`, `*.rknn`), 원천 데이터(`data/`), `.env`, API 키는 커밋 금지.

## 4. Pull Request

- PR 제목은 커밋 규칙과 동일하게 쓴다.
- 본문에 반드시 포함: 변경 이유, 확인 방법(실행·테스트 절차), 스크린샷(UI 변경 시).
- 리뷰어 1명 이상 승인 후 병합한다. 자기 PR은 자기가 병합하지 않는다.
- PR 하나는 300줄 이내를 목표로 한다. 커지면 나눈다.
- 리뷰 요청 후 24시간 안에 응답한다. 바쁘면 "내일 본다"라도 남긴다.
- CI가 빨간 상태면 병합하지 않는다.

## 5. API 계약

- 백엔드 라우트·스키마를 바꾸면 같은 PR에서 `docs/api/API_SPEC.md`를 갱신하고 프론트 담당을 리뷰어로 넣는다.
- 프론트 `types/`는 백엔드 OpenAPI(`/docs`)를 기준으로 맞춘다. 임의로 필드를 추가하지 않는다.
- 모델 클래스 번호와 백엔드 seed의 `model_class_id`는 항상 일치시킨다. 클래스 추가는 모델 담당과 백엔드 담당이 함께 한다.

## 6. 코드 규칙

- 프론트: `npm run lint` 통과. 컴포넌트는 `features/<도메인>/` 아래에 둔다.
- 백엔드: `pytest` 통과. 새 라우트는 테스트를 같이 넣는다.
- 모델: 학습·평가 결과는 `ml/README.md`에 날짜, 데이터 규모, 클래스별 정확도를 기록한다.
- 로컬에서 실행해보지 않은 코드는 PR에 올리지 않는다.

## 7. 문서와 보고

- 문서는 [문서 목차](../README.md)의 카테고리에 추가한다. 주간보고·작업보고·제출본은 `docs/reports/weekNN_YYYYMMDD-YYYYMMDD/`에 보관하고, 제출 양식은 `docs/templates/`에 보관한다.
- 주간보고 담당 로테이션: 김헌영(2주) → 고명준(3주) → 김민서(4주) → 박성호(5주) → 이서하(6주) → 반복.
- 주간보고 담당은 일요일까지 각 파트 진행 내용을 취합해 `docs/reports/weekNN_YYYYMMDD-YYYYMMDD/주간보고_YYYYMMDD.md`로 작성하고 hwp 양식에 옮긴다.
- 각자 자기 파트 진행 상황을 일요일 저녁까지 담당자에게 전달한다.

## 8. 소통

- 막히면 하루 이상 붙들지 말고 팀 채널에 올린다.
- 회의 결정 사항은 당일 노션 또는 해당 주차의 `docs/reports/` 폴더에 기록한다. 기록 없는 결정은 없는 것으로 본다.
- 일정을 못 지킬 것 같으면 마감 전에 미리 말한다.

## 9. 보안·비공개

- 특허 출원 전이므로 재촬영 유도 알고리즘의 세부 수치·판별 규칙은 발표 자료와 공개 문서에 넣지 않는다.
- AI Hub 데이터는 이용 약관에 따라 저장소 밖에서만 관리한다.
- 마음AI 등 외부 협력사에서 받은 자료는 팀 채널 밖으로 공유하지 않는다.
