# Figma 백엔드 보완 실행 계획

승인 근거: 2026-10-08 검토 보고서에 대한 사용자의 “위 작업 진행하자”. 기존 FastAPI/SQLite/Next.js 흐름을 확장한다. Figma는 변경하지 않는다.

## 범위와 계약

1. 이력: `severity=high|medium|low` 필터, 요약의 category/severity/is_refined, 전체·작물·필터 건수. 과거 기록은 새 스냅샷이 없으면 현재 참고값임을 명시한다.
2. 스냅샷: 병해 안내와 관리 행동·농약 조회를 JSON으로 저장. 농약은 당시 조회와 현재 카탈로그를 응답에서 구분한다. 신규/재촬영 결과 모두 버전과 시점을 보존한다.
3. 판정: 기존 프론트 기준 0.5를 서버 설정으로 이동. 주 상태와 이유, 정책 버전 제공. 재촬영 후에도 혼동을 다시 평가한다. 사진별 중증도 분석이나 OOD 성능은 구현 완료로 주장하지 않는다.
4. 오류: 기존 detail을 유지하고 code/request_id/retryable 추가. 업로드·검증·모델·기록·저장 실패 구분. 파일 정책 조회 제공.
5. 복구: 정상 자동 저장 유지. API 경로에서는 저장 실패 결과를 서버 전용 디스크 초안으로 보존하고 save_status=failed/recovery_token을 반환. 복구 토큰으로 다시 저장하되 모델 추론을 다시 하지 않는다. 초안 보관 자체가 실패하면 복구 성공을 약속하지 않고 오류를 반환한다.
6. 멱등성: 선택적인 Idempotency-Key와 본문 지문. 성공 응답을 DB에 같은 트랜잭션으로 보존. 키/사진/작물이 달라지면 409. 재촬영 복구는 revision을 확인하고 이후 결과를 덮어쓰지 않는다.
7. 연동: 프론트 API 타입/오류/재시도 키, 이력 필터와 저장 복구, 서버 판정과 관리 행동 사용. 기존 반응형 UI를 유지한다.
8. 오프라인: 실행 경로에 대한 사용자 답변에 맞춰 별도 범위 확정. 우선 로컬 서버의 준비 상태·파일/모델/콘텐츠 정책을 제공한다. 스마트폰 추론·실제 음성·농약 실동기화는 모델/기기 검증 없이 완료로 표시하지 않는다.

## 구현 순서와 검증

- 기존 테스트 fixture 패턴으로 이력 필터·스냅샷·판정 테스트를 먼저 추가하고 실패를 확인한다.
- additive migration과 모델/schema/service/API를 수정하고 관련 테스트를 실행한다.
- 오류·멱등·저장 복구 테스트를 먼저 추가한다. 저장 실패·응답 유실·재촬영 충돌·복구 토큰 오염/만료를 검증한다.
- 프론트 연동 후 TypeScript 검사·빌드를 실행한다.
- 전체 백엔드 테스트를 새 workspace 임시 경로에서 실행한다. 실제 운영 DB를 테스트에 사용하지 않는다.
- API 문서에 새 필드·엔드포인트·호환성과 복구 보관 한계를 기록한다.

실행: 현재 세션에서 직접 진행. 기존 사용자 변경을 덮어쓰지 않고 관련 파일만 수정한다.
