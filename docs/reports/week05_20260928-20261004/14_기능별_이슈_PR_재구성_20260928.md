## 2. 병합 순서

- 백엔드: **#18 DB → #19 모델·진단 → #20 업로드 → #21 농약·결과 연동**.
- ML: **#22 기존 실험 → #23 데이터 감사·분할 → #24 224/256 평가**.
- LLM 계획 **#25**는 develop 대상 독립 PR이다.
- 공통 문서 **#26**은 #24 위의 문서 차이만 표시하며, **#24·#21·#25가 모두 develop에 병합된 뒤** 상대 링크와 기능 설명을 확인하고 병합한다.

후속 PR을 선행 기능 브랜치에 바로 병합하지 않는다. 팀의 Squash 규칙에 따라 선행 PR을 develop에 병합한 뒤, 후속 PR의 **고유 커밋만** 최신 develop 위로 다시 배치하고 base를 develop으로 변경한다. 파일 차이·테스트를 재확인한 뒤 Draft를 해제한다. 선행 브랜치를 먼저 삭제하거나 단순히 base만 변경하면 이전 변경이 다시 나타날 수 있다. 이번 재구성 과정에서 병합·강제 푸시·기존 브랜치 삭제는 하지 않았다.

`Closes #번호`는 연결을 표시하지만 자동 종료는 GitHub 기본 브랜치 규칙의 영향을 받는다. develop 병합 후 개별 이슈 상태를 확인하고, 모든 하위 작업이 끝난 뒤 상위 이슈 #5·#6을 닫는다.

## 3. 검증과 범위

| 단계 | 분리 작업 트리 검증 |
|---|---|
| DB | pytest 35 passed |
| 모델·진단 | pytest 103 passed |
| 업로드 | pytest 139 passed, 1 skipped |
| 농약·최종 연동 | pytest 183 passed, 1 skipped |

| ML 저장 지표 | 혼동행렬에서 224=721/785, 256=726/785 재계산 일치 |

건너뛴 테스트는 Windows symlink 관련이다. 기존 최종 frontend 코드와의 동일성을 확인했지만 이번 분리 과정에서 프론트 빌드를 재실행한 것은 아니다. 이전 빌드의 standalone 복사 EPERM 경고, UI 스크린샷·실기기·Docker/ARM64 검증은 남아 있으며 #21을 Draft로 유지한다. GPU 재학습과 test 평가는 하지 않았다.

API 변경 문서는 해당 백엔드 단계에 포함했다. 농약 응답을 포함한 최종 프론트 타입·결과 표시·이력 연동은 #21에 모았다. 회귀 테스트·시드·예측 CSV 등 기능 검증 자료 때문에 일부 PR은 300줄 권장 규모를 넘지만, 서로 다른 파트의 변경을 한 PR에 합치지 않았다.

Git은 기존 `ml` 브랜치와 `ml/...` 이름을 동시에 허용하지 않으므로 기존 링크를 보존하기 위해 새 ML 브랜치 접두사는 `model/`로 정했다. 각 PR은 확인된 팀원 계정에 리뷰를 요청했으며 API 계약은 API·프론트 공동 검토가 필요하다.

## 4. 이번 재게시에서 제외한 자료

- 사용자가 보류한 **256 오류 59장 원인 검토**는 로컬에 보존하며 이번 PR에 포함하지 않았다.
- 최신 xpdocs PDF는 Markdown 변경 전 스냅샷일 수 있어 제외하고 Markdown을 기준으로 한다. 단, `report/데이터셋_구축_및_성능_개선_결과_보고서_3주차_4주차.pdf`는 3·4주차 제출본 보존을 위해 포함했다. 이 PDF는 제출 당시 스냅샷이며 최신 PR 상태를 나타내지 않는다.
- 원천 이미지·라벨·체크포인트·학습 ZIP·환경 비밀은 제외했다.
- 전체 명칭 변경·발표 자료 등 원래 두 PR 밖의 로컬 커밋은 보존 브랜치에 그대로 둔다.
