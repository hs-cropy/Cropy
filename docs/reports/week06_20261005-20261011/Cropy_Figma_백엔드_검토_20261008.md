# Cropy Figma 디자인 기반 백엔드 검토

기준일: 2026-10-08 · 대상: `C:\cropy`의 현재 작업본과 연결된 Figma 파일. 배포 서비스의 동작을 검증한 문서는 아니다.

기본 진단과 S2 재촬영의 핵심 처리는 이미 구현되어 있다. 최신 디자인을 그대로 구현하려면 이력 등급 필터, 저장 실패 복구, 저장 당시 안내 보존, 일관된 판정 정책과 오류 식별을 보완해야 한다. 오프라인·음성 화면은 별도 개발 범위다.

이번 검토에서는 Figma와 애플리케이션 코드를 변경하지 않았다. 이 보고서만 새로 추가했다.

## 3. 최신 화면 구현에 우선 필요한 보완

### P0-1. 등급별 이력 필터와 카드 데이터

디자인은 작물 3종 × 등급 4종(전체·위험·주의·낮음)을 함께 적용하고 실제 건수와 카드 등급을 표시한다.

현재 `/history`에는 `crop_type`, `page`, `size`만 있다. `DiagnosisSummary`에는 `severity`와 `category`가 없으며, `total`은 적용된 작물 조건의 건수다. 따라서 전체 이력이 없는지, 선택한 등급에만 기록이 없는지 응답 하나로 구분하기 어렵다. 프론트 `fetchHistory()`도 현재 작물 필터를 전달하지 않는다.

- API에 등급 필터를 추가하고 결과 목록·건수에 동일한 조건을 적용한다.
- 요약에 등급과 정상/병해 구분을 추가한다. 재촬영 표시는 기존 `refined_image_url`로도 구현할 수 있으므로 전용 필드는 선택 사항이다.
- 필터 조건을 적용하기 전 건수 또는 작물별 전체 건수를 함께 제공해 두 종류의 빈 상태를 구분한다.
- `high/medium/low`와 화면의 위험/주의/낮음 매핑을 하나로 확정한다. 현재 severity는 병해 시드의 고정 값이지 사진별 병반 면적을 분석한 중증도는 아니다.
- 모든 페이지를 받지 않고 첫 페이지 20건만 로컬 필터링하면 건수가 틀릴 수 있으므로 서버 필터를 사용한다.

근거: `api/routes/diagnosis.py:124`, `services/diagnosis_service.py:205`, `schemas/diagnosis.py:83`, `frontend/src/lib/api.ts`.

### P0-2. 저장 당시 안내를 보존하는 기록 구조

디자인과 S5는 저장 당시의 결과·안내·추천 농약을 조회하도록 요구한다.

현재 `_response()`는 매번 `Diagnosis.disease`의 현재 description·causes·prevention·severity와 현재 농약 카탈로그를 읽는다. 진단 점수와 사진은 저장되지만 안내 본문은 스냅샷으로 보존되지 않는다. 콘텐츠나 카탈로그를 갱신하면 과거 기록의 안내도 바뀐다.

- 저장 시 병해명·등급·설명·원인·예방·관리 행동과 콘텐츠 버전을 함께 보존한다.
- 당시 농약 조회 내용과 검증 출처·조회 시점을 보존하되, 과거 안내와 현재 조회 정보를 구분한다.
- 기록 화면에 과거 농약 내용을 현재 사용 가능 정보로 표시하지 않도록 구분 상태를 전달한다.
- 재촬영으로 결과를 갱신할 때 갱신 결과의 스냅샷도 함께 저장한다. 1차 결과와 비교하는 UI가 필요하면 초기 후보도 별도로 반환한다. 현재 전체 초기 분포는 DB의 `original_predictions`에 있으나 응답에는 없다.
- 기존 기록에는 당시 안내를 소급 복원할 수 없으므로 누락/현재 참고 안내 상태를 명시한다.

근거: `services/diagnosis_service.py:97`, `models/entities.py:59`.

### P0-3. 분석 성공과 저장 실패를 분리하는 복구 계약

V3에는 저장 중, 저장 실패, 다시 저장, 저장 완료 토스트, 미저장 이탈 확인이 있다.

현재 진단과 저장은 한 요청·한 트랜잭션이다. DB 커밋이 실패하면 API는 성공한 분석 결과를 반환하지 않고 새 사진도 정리한다. 별도 저장 재시도 API는 없다. 따라서 현재 계약으로는 '이번 결과는 볼 수 있지만 저장은 실패했다' 화면을 구현할 수 없다.

- 기존 정상 경로의 자동 저장은 유지한다.
- 저장 실패에도 결과를 화면에 남길 요구를 채택하면 `save_status`와 복구 가능한 결과 식별자를 포함하는 응답을 설계한다.
- 재분석 없이 서버가 발급·검증한 결과를 다시 저장할 방법을 제공한다. 임시 결과 저장 방식은 DB/디스크 장애 시 생존 범위와 만료 정책까지 정한다.
- 클라이언트가 임의로 제출한 병명·농약 권고를 서버 모델 진단으로 신뢰하지 않는다.
- 같은 저장 재시도로 두 기록이 생기지 않게 한다.
- 단일 원자 저장 정책을 계속 쓴다면 저장 실패/다시 저장 시안은 조건부로 제외해야 한다. 디자인의 가이드도 실제 미저장 손실이 있을 때만 확인창을 사용하도록 명시한다.

근거: `services/diagnosis_service.py:115–142`, `tests/test_diagnosis_integrity.py`의 커밋 실패 테스트. 새 계약을 도입하려면 이 테스트의 기대도 함께 재검토해야 한다.

### P0-4. 화면 전환에 쓸 판정 정책

디자인은 성공·낮은 신뢰도·후보 혼동을 서비스 응답/정책으로 구분하며 UI에서 임의 임계값을 추가하지 않도록 요구한다.

현재 서버는 혼동쌍 `recapture`와 `crop_mismatch`를 반환하지만 일반 낮은 신뢰도 상태는 반환하지 않는다. 프론트 `DiagnosisResult.tsx`에는 `LOW_CONFIDENCE = 0.5`가 별도로 있다.

- 낮은 점수·혼동쌍·작물 불일치·정상·일반 병해를 구분하는 정책을 한 곳에서 관리하고 정책 버전을 기록한다.
- API에 판정 상태와 안내 사유를 제공한다. 상태가 동시에 발생할 수 있으므로 주 상태와 사유 목록을 나눌 수 있다.
- 2차 촬영 후에도 혼동이 남는 경우를 재평가한다. 현재 refine는 점수와 무관하게 `recapture = None`으로 정리한다.
- '재촬영으로 갱신됨'과 '충분히 구분됨'을 같은 의미로 처리하지 않는다.
- 잎이 아닌 사진이나 지원 외 작물을 일반 병해로 분류하지 않기 위한 품질/OOD 처리는 ML 검증 과제다. 9클래스 softmax 점수가 낮다는 조건만으로 이를 보장할 수 없다.

근거: `services/recapture.py`, `services/diagnosis_service.py:187`, `frontend/src/components/DiagnosisResult.tsx:14`.

### P0-5. 식별 가능한 오류 응답과 파일 정책

400·413·404·409·503 처리는 이미 있다. 다만 같은 HTTP 상태에 여러 원인이 포함되고 응답은 주로 `detail` 문자열이다. 형식 오류와 사진 디코딩 오류, 파일 크기와 해상도 초과, 모델 사용 불가를 화면별로 안정적으로 매핑하기 어렵다. DB 저장 실패도 전용 응답 계약이 없다.

- 기존 detail과 호환되는 구조에 `code`, `request_id`, 필요시 `retryable`을 추가한다.
- 요청 검증 422도 같은 규칙으로 처리한다. 서버 오류를 인터넷 연결 끊김으로 표시하지 않는다.
- 설정에 있는 허용 파일 형식·최대 바이트·최대 픽셀을 클라이언트와 공유해 선택 안내와 서버 제한이 일치하게 한다.
- 인터넷/카메라/브라우저 저장 공간 오류는 클라이언트에서 판별하고, 서버 장애와 분리한다.

예시 코드: `UNSUPPORTED_IMAGE_FORMAT`, `INVALID_IMAGE`, `IMAGE_TOO_LARGE`, `IMAGE_RESOLUTION_TOO_LARGE`, `MODEL_UNAVAILABLE`, `DIAGNOSIS_NOT_FOUND`, `MODEL_VERSION_CONFLICT`, `SAVE_FAILED`. 새 코드명을 실제 계약으로 확정한 상태는 아니다.

### P1-1. 재시도 중복 방지와 취소 의미

버튼 비활성화와 동시 추론 Semaphore는 있지만 요청의 멱등성은 없다. 최초 저장은 완료됐는데 응답이 끊긴 뒤 다시 요청하면 새 UUID로 중복 이력이 생길 수 있다. 재촬영의 revision 충돌 보호도 네트워크 재시도 중복과는 다르다.

- 진단·재촬영·저장에 동일 요청을 식별하는 키를 적용한다. 다른 사진/조건에 같은 키를 재사용할 때의 충돌 규칙도 정한다.
- 프론트에서 이전·취소 요청의 늦은 응답이 현재 화면을 덮어쓰지 않게 한다.
- 현재 서버에는 취소 API가 없다. 브라우저 요청 취소만으로 추론·자동 저장까지 취소됐다고 알리지 않는다.
- 짧은 진단은 동기 요청을 유지할 수 있다. 서버 작업의 실제 취소와 완료 후 조회가 요구될 때만 작업 ID·상태 조회·취소를 도입한다.
- 지연/시간 초과 문구는 실제 정책과 연결한다. 현재 Semaphore의 대기 제한이나 진단 전체 기한은 별도로 정의돼 있지 않다.

### P1-2. '지금 해야 할 일'과 농약 카드 데이터

디자인의 관리 행동 3가지는 현재 응답 필드로 구조화돼 있지 않다. `causes`·`prevention`은 있으나 즉시 관리 행동과 예방 행동은 같은 의미가 아니다.

- 병해별 검수된 관리 행동을 정렬된 목록으로 제공한다. 모든 병해에 고추 탄저병용 문구를 재사용하지 않는다.
- 농약의 source·verification_status·synced_at은 이미 있다. 최신 동기화 성공 여부, 갱신 시점, 빈 카탈로그 사유를 보완하면 정보 없음과 갱신 실패를 구분할 수 있다.
- S1의 '3회 이내'에 해당하는 사용 횟수는 현재 PSIS 동기화에서 `safety_notes` 문자열에 포함될 수 있지만 전용 구조 필드는 없다. 별도 카드 항목으로 표시하려면 원본 조건을 검증해 구조화한다.
- 현재 검증 상태는 출처/검증 여부를 나타내며 별도의 최신성 기한 정책은 아니다.
- 시나리오의 1,000배·7일·3회를 운영 값으로 하드코딩하지 않는다. 이번 검토에서 PSIS 실제 갱신이나 사용 기준 검증은 하지 않았다.

## 4. 오프라인·온디바이스는 두 경로로 구분

| 경로 | 현재 구현과의 관계 | 추가 작업 |
|---|---|---|
| Orange Pi에서 FastAPI·CNN·SQLite 실행, 폰/화면은 접속 | 기존 로컬 서버 구조를 활용 가능. 폰은 보드와 연결돼 있어야 함 | ARM64/모델 런타임 설치, 모든 실행 자산의 로컬 제공, 자동 시작·복구, 저장 공간 확인, 네트워크/HTTPS·실기기 검증 |
| 스마트폰 브라우저에서 자체 추론·저장 | 현재 폰은 API 클라이언트. 브라우저 추론·PWA·로컬 진단 DB는 미구현 | 웹용 모델 변환·검증, 브라우저 추론, 화면/폰트/런타임/안내 캐시, 로컬 사진·이력 저장, 모델 업데이트·복구 |

Service Worker는 오프라인 자산 캐시를 지원하지만 HTTPS 또는 신뢰 가능한 개발 오리진이 필요하다. 캐시만 추가해 서버 추론이 폰 내부 추론으로 바뀌지는 않는다. [MDN Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)

브라우저 추론 후보로 ONNX Runtime Web을 검토할 수 있으나 지원 연산·기기·실행 공급자와 모델 변환 정확도를 실제로 확인해야 한다. 브라우저 저장은 용량 제한·퇴거 가능성이 있어 로컬 기록을 서버 백업으로 표시하면 안 된다. [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/), [MDN 저장 용량·퇴거](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

브라우저 온디바이스 경로를 채택할 경우의 백엔드 역할:

- 모델·전처리·클래스 매핑·병해 콘텐츠 버전, 파일 URL·크기·해시를 포함한 배포 목록 제공.
- 로컬에서 모델 검증 후 활성화하고, 실패하면 이전 정상 버전을 유지하는 클라이언트와 호환.
- 서버 동기화를 제공하는 경우에만 로컬 기록 업로드 API 추가. `client_record_id`/요청 키로 중복 방지, 출처·모델·콘텐츠 버전과 사진 연결 보존.
- 로컬 추론 점수를 서버에서 검증한 진단으로 표시하지 않도록 출처 구분.
- 동기화 충돌·재촬영 갱신·부분 업로드 실패 정책 정의.
- 저장 공간 관리·내보내기·선택 삭제는 대상 저장소에 맞춰 구현. 현재 백엔드는 이력 삭제/내보내기 API가 없고 고아 업로드 정리 스크립트만 있다.

서버 동기화를 제공하지 않는 단독 로컬 모드라면 sync-pending/sync-failed 화면과 서버 동기화 API는 필요하지 않다. Figma 가이드도 이를 조건부 상태로 정의한다.

## 5. 음성과 사용자 분리

단순 결과 읽기는 프론트/로컬 TTS로 구현할 수 있으며 반드시 서버 API가 필요한 기능은 아니다. 실제 음성 명령으로 촬영·재촬영·이력을 제어하는 S3·S4에는 STT·명령 처리·진단 연결·TTS·재시도와 오프라인 음성 런타임 통합이 필요하다. 현재 앱에 이 통합은 없고 문서/데이터 준비 단계다. 새 모바일 음성 전용 섹션 `677:17569`에서는 검토할 텍스트가 없어 완성된 상세 요구사항으로 취급하지 않았다.

현재 진단과 이력은 사용자/농장 구분 없이 공유되고 `/uploads`도 인증 없이 제공된다. Figma 시나리오에서 로그인은 Phase 2 범위이므로 단일 장치 시연 때문에 인증을 즉시 새로 만들 필요는 없다. 여러 농가가 접속하는 서비스로 배포하려면 기록 소유권·인증·사진 접근 권한을 동기화/삭제 기능과 함께 설계해야 한다.

## 6. 프론트에서 처리할 항목

마스코트·토스트·단일 버튼 중앙 정렬·다이얼로그·아코디언·큰 글자·반응형·필터와 스크롤 복원은 프론트 작업이다. 24개 피드백 화면마다 API를 만들 필요는 없다.

카메라 권한·스트림 끊김, 선택 사진 유지, 업로드 전 형식 확인, 사진 로드 실패 대체 UI, 요청 로딩·지연 표시, 로컬 저장 용량과 다운로드 바이트 진행률도 클라이언트 책임이다. 백엔드는 실제 결과·저장 상태·식별 가능한 실패 원인·공유 정책을 제공한다.

## 7. 권장 작업 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 등급 필터·카드 응답 | 세 작물 × 네 등급에서 건수/목록 일치, 페이지네이션 이후도 동일, 전체 빈 상태 구분 |
| 2 | 판정·오류·파일 정책 | 웹/모바일의 상태 분기 일치, 400/413/404/409/422/503와 브라우저 오류 구분 |
| 3 | 기록 스냅샷·관리 행동 | 콘텐츠 갱신 후 과거 안내 보존, 신규 기록에 해당 병해의 행동 표시 |
| 4 | 저장 복구·멱등성 | 저장 실패 후 결과 유지와 재시도, 응답 유실 후 중복 기록 없음 |
| 5 | S1·S2 통합 검증 | 진단→이력, 혼동쌍→재촬영→두 사진·갱신 결과·기록까지 실동작 |
| 6 | 오프라인 경로 구현 | 서버/인터넷 연결 단절을 각각 시험, 실제 기기에서 추론·저장·업데이트 실패 복구 |
| 7 | 음성·다중 사용자 | 채택한 기능 범위에서 실제 STT/TTS와 소유권 검증 |

S1의 5초 이내 응답은 목표일 뿐 이번 테스트로 달성 확인하지 않았다. S2의 재촬영 정확도 개선, 무 노균병 재현율, 실제 촬영 1분 이내 사용성도 별도 평가 대상이다. 시연 점수와 시간을 고정해 목표를 충족한 것으로 처리하지 않는다.

## 8. 검증 기록과 한계

- 기존 백엔드 테스트 전체를 임시 DB·업로드 경로에서 실행: **183 passed, 1 skipped**, 28.56초, exit code 0.
- 첫 실행은 기본 pytest 임시 폴더의 `PermissionError: WinError 5`로 104개 setup 오류가 발생했다. 작업공간 안에 새 임시 경로를 지정하자 해소됐다. 제품 코드를 수정하지 않았다.
- 건너뛴 테스트는 호스트의 심볼릭 링크 생성 지원에 따른 조건부 테스트다.
- 최종 명령: `.venv/Scripts/python.exe -m pytest tests -q -p no:cacheprovider --basetemp <새 작업공간 임시 경로>/pytest --tb=short`.
- 기존 테스트 통과는 기존 계약 검증이다. 본문에 제안한 새 필터·저장 복구·오프라인·음성 기능의 구현 완료를 뜻하지 않는다.
- 배포 서비스, PSIS 실연동, 보드/스마트폰 속도, 실제 오프라인 모델, 사람의 병해·농약 콘텐츠 검수는 확인하지 않았다.
