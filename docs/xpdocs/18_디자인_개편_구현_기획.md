## 1. 목표와 범위

**목표**: 현재 화면(노랑·갈색 팔레트, 화면마다 직접 쓴 스타일)을 새 Figma 디자인(초록·회색 팔레트, 마스코트, 고정 틀)으로 옮긴다. 옮기는 과정에서 디자인 토큰과 공통 컴포넌트를 먼저 만들고, 화면은 그것을 조립해서 만든다. 같은 모양을 두 번 구현하지 않는 것이 기준이다.

| 범위 안 | 범위 밖 |
|---|---|
| 디자인 토큰(색·radius·크기·글자) 도입과 옛 토큰 정리 | 백엔드 API·응답 스키마 변경 |
| 공통 컴포넌트와 Storybook 문서화 | 오프라인·온디바이스 전용 상태 화면 (Figma에서 "추가안", 12절 결정 6) |

## 3. 설계 원칙

확장성과 재사용성을 지키기 위한 규칙이다. 리뷰에서 이 규칙을 기준으로 본다.

0. **디자인 시스템을 따르되, 화면이 다르면 화면이 우선이다.** 컴포넌트를 만들 때 디자인 시스템의 `Cropy/V2/*` 원본과 화면에 쓰인 모습을 둘 다 확인한다. 다른 곳이 있으면 화면 값으로 구현하고 13절에 적는다. 화면 쪽이 옛 버전으로 보이면 임의로 정하지 않고 확인한다.
1. **값은 토큰에서만 온다.** 컴포넌트에 색상 코드나 px 값을 직접 쓰지 않는다. Figma에 변수가 없는 값(4.3절)만 예외이고, 그 경우 컴포넌트 안에 이유를 주석으로 남긴다.
2. **토큰 이름은 Figma 변수 이름을 따른다.** `--cropy-color-green-600` → `cropy-green-600`. 디자인이 바뀌면 이름으로 바로 찾을 수 있어야 한다.
3. **치수는 rem으로 쓴다.** 큰 글자 모드가 루트 글자 크기를 125%로 키우는 방식이라, px로 쓰면 커지지 않는다.
4. **컴포넌트는 모양만 알고 데이터는 모른다.** 공통 컴포넌트는 API를 부르거나 라우트를 알지 않는다. 문구·데이터·동작은 props로 받는다.
5. **변형은 props로, 새 모양은 디자인 확인 후에.** `variant`, `size` 같은 정해진 값으로만 모양을 바꾼다. Figma에 없는 변형이 필요하면 임의로 만들지 않고 디자이너에게 먼저 확인한다.
6. **`className`은 배치용이다.** 호출부는 폭·여백·정렬만 넘긴다. `cn`으로 병합되므로 색이나 크기 클래스를 넘기면 실제로 덮이는데, 그렇게 쓰지 않는다.
7. **상태가 같으면 문구도 같다.** 피드백 문구는 케이스 ID로 한 곳에서 관리한다(5.4절). 화면에 문구를 직접 쓰지 않는다.
8. **접근성은 컴포넌트가 책임진다.** 초점 표시, 키보드 조작, `aria-*` 속성은 공통 컴포넌트 안에서 처리해 화면마다 다시 구현하지 않는다.
9. **스토리와 테스트가 없으면 완성이 아니다.** 10절의 완료 기준을 따른다.
10. **한 번에 하나씩 옮긴다.** 화면 단위로 PR을 나누고, 옮긴 화면은 옛 토큰을 쓰지 않는다. 섞인 상태는 화면 "사이"에만 허용한다.

## 4. 디자인 시스템

### 4.1 토큰 (도입 완료)

`frontend/tailwind.config.js`에 디자인 시스템의 변수와 글자 스타일을 `cropy-*` 이름으로 추가했다. 옛 토큰과 함께 있고, 새 컴포넌트는 `cropy-*`만 쓴다.

| 색 — 글자 | `text-primary` `#191919`, `secondary` `#6b6b6b`, `disabled` `#a5a5a5`, `on-action` `#ffffff` | `text-cropy-text-primary` |

### 4.2 토큰을 추가하는 절차

1. Figma에 변수가 있는지 확인한다. 없으면 디자이너에게 변수로 만들어 달라고 요청한다.
2. `tailwind.config.js`에 Figma 이름 그대로 추가하고, 치수는 rem으로 변환한다.
3. 색이 아닌 토큰이면 `src/lib/cn.ts`에도 등록한다. 빠뜨리면 `cn.test.ts`가 실패한다.
4. 같은 PR에서 그 토큰을 쓰는 컴포넌트의 스토리로 확인한다.

### 4.3 디자인 시스템에 변수가 없는 값

컴포넌트에는 쓰이지만 변수가 아니라 직접 입력된 값이다. 지금은 컴포넌트에서 직접 지정하고, 변수가 생기면 토큰으로 옮긴다.

| 값 | 쓰이는 곳 | 지금의 처리 |
|---|---|---|
| radius 10px | 피드백 카드 안 버튼 | 컴포넌트에서 `rounded-[0.625rem]` |
| radius 18px | 피드백 카드 | 옛 `rounded-card`와 값이 같아 그대로 사용 |
| 토스트 배경(짙은 녹색) | 토스트 | Toast 구현 때 값 확인 필요 |
| 키보드 초점 표시 | 버튼·스위치 등 | `action-primary` 색 2px 외곽선 (디자인 시스템에 상태 정의가 없음) |
| 진행 중(loading) 버튼, 아이콘이 든 버튼 | 버튼 | 색을 유지하고 스피너·아이콘을 라벨 앞에 둠 (정의 없음) |

### 4.4 옛 토큰의 정리

옛 토큰(`brand`, `ink`, `muted`, `line`, `khaki`, `brown`, `paper`, `signal-*`, `shadow-cta` 등)은 화면을 다 옮길 때까지 남긴다. 현재 사용처는 `brand` 계열 29곳, `ink` 36곳, `line` 15곳이다.

- 화면을 옮기는 PR마다 그 화면에서 옛 토큰 클래스가 0건인지 검색으로 확인한다.
- 모든 화면을 옮긴 뒤 옛 토큰을 삭제하는 PR을 따로 낸다. 삭제 후 `npm run build`가 통과하면 남은 사용처가 없는 것이다.
- 디자인 시스템의 등급 배지는 "주의"에 `status-attention`을 쓴다. `signal-med`도 다른 옛 토큰과 함께 지운다(12절 결정 7에서 주의 색이 따로 정해지면 그 값으로 토큰을 추가).

## 5. 공통 컴포넌트

### 5.1 계층과 폴더

| 계층 | 위치 | 성격 | 예 |
|---|---|---|---|
| 기본 | `src/components/` | 도메인을 모르는 최소 단위. props만으로 동작 | Button, Switch, Badge, Chip, Card, Spinner, Mascot, Logo |
| 조합 | `src/components/` | 기본 컴포넌트를 묶은 패턴. 여전히 도메인을 모름 | ConfirmDialog, Toast, InlineFeedback, Accordion, EmptyState, PageHeader, ActionBar |
| 틀 | `src/components/` | 앱 전체에 한 번 쓰이는 골격 | Header, MobileNav, AppShell |
| 기능 | `src/features/<도메인>/components/` | 도메인 데이터와 API를 아는 컴포넌트. 공통 컴포넌트를 조립 | HistoryList, DiagnosisSummary, CropGradeFilter, CameraCapture |

- 팀 규칙(10번 문서 6절)은 "컴포넌트는 `features/<도메인>/` 아래"다. 공통 컴포넌트만 `src/components/`에 두고, 지금 `src/components/`에 있는 도메인 컴포넌트(`DiagnoseForm`, `DiagnosisResult`, `RecapturePanel`, `SaveRecovery`)는 해당 화면을 옮길 때 `features/diagnosis/`로 옮긴다.
- 공통 컴포넌트 파일은 한 폴더에 평평하게 둔다: `Button.tsx`, `Button.test.tsx`, `Button.stories.tsx`. 배럴(`index.ts`)은 만들지 않고 `@/components/Button`으로 불러온다(현재 관례).

### 5.2 API 규칙

- named export, props는 `interface`로 선언하고 HTML 요소의 속성을 확장한다(`ComponentPropsWithRef<"button">`). `ref`와 `aria-*`가 그대로 전달돼야 한다.
- 모양을 바꾸는 props 이름은 통일한다: `variant`(종류), `size`(크기), `fullWidth`, `disabled`, `loading`.
- 클래스는 `cn()`으로 합치고, 변형별 클래스는 완성된 문자열 표로 둔다. 문자열을 조각내 이어 붙이면 Tailwind가 클래스를 찾지 못한다.
- 버튼이 아닌 요소(Link, 파일 선택 label)에 같은 모양이 필요하면 클래스 함수를 함께 내보낸다(`buttonClassName`).
- 훅이 없으면 `"use client"`를 붙이지 않는다. 서버 컴포넌트에서도 쓸 수 있게 둔다.

### 5.4 피드백 문구 사전

Figma의 피드백 24종은 모양이 3가지뿐이고 문구만 다르다. 컴포넌트를 24개 만들지 않고, 문구를 케이스 ID로 모은 사전 하나와 컴포넌트 3개로 구현한다.

```ts
// src/features/feedback/cases.ts (예시)
export const FEEDBACK = {
  "discard-photo": {
    kind: "dialog",
    mascot: "confirmation",
    title: "선택한 사진을 지울까요?",
    message: "나가면 선택한 사진이 초기화돼요.\n사진을 유지하려면 계속 확인해주세요.",
    primary: "계속 확인하기",   // 유지하는 쪽이 초록
    secondary: "지우고 나가기",
  },
  // …
} as const;
```

- 케이스 ID는 Figma 컴포넌트 이름과 같게 둔다 (`discard-photo`, `analysis-timeout`, `save-failed` …).
- `public/mobile-prototype/states.js`에 같은 ID로 정리된 문구가 이미 있다. 옮겨 쓰되, 정적 프로토타입용 파일이라 직접 import하지 않고 내용을 가져온 뒤 Figma와 대조한다.
- 음성 안내 문장(`features/voice/lib/prompts`)과 같은 뜻의 문장은 화면 문구와 어긋나지 않게 함께 본다.

**Figma 가이드가 정한 동작** (구현할 때 지킬 것)

- 다이얼로그는 사진·진행 중 분석·저장 안 된 결과를 실제로 잃는 경우에만 띄운다. 배경 조작을 막고 초점을 안에 가둔다.
- 토스트는 한 번에 하나, 기본 4초. 행동 영역이나 내비 위 16px에 띄우고 버튼을 가리지 않는다.
- 필터 변경, 큰 글자 변경, 사진 선택 성공, 분석 완료, 아코디언 펼침에는 확인창이나 토스트를 띄우지 않는다.
- 큰 글자 모드에서 버튼 2개는 세로로 쌓고 높이를 늘린다. 버튼 글자를 줄이지 않는다.
- 색만으로 뜻을 전하지 않는다. 장식용 마스코트는 스크린리더에서 제외한다.
- 피드백 카드의 그림은 모바일 64px, 데스크탑 80px이다. 디자인 시스템은 원형·삼각형 아이콘이지만 화면은 마스코트(V3)로 바뀌어 있어, 화면을 따라 마스코트를 쓴다.
- 토스트는 일반 완료 알림에, 오류·재시도는 지속형 안내에, 작업 손실은 확인 다이얼로그에 쓴다.

### 6.2 구조가 바뀌는 부분

- **3탭 내비게이션.** 지금은 진단(`/`)·이력(`/history`) 2탭이고, 촬영은 진단 화면 위에 뜨는 오버레이다. 새 디자인은 촬영이 독립 탭이다. 라우트를 어떻게 나눌지는 12절 결정 4에서 정한다. `/camera` 페이지를 한 번 만들었다가 삭제한 이력이 있으므로 그 이유를 먼저 확인한다.
- **고정 틀.** 헤더·제목·행동 영역·내비는 고정하고 본문만 스크롤한다. 지금은 페이지 전체가 스크롤된다. `AppShell`이 높이를 나누고, 화면은 본문과 행동 영역의 내용만 채운다.
- **이력 복귀.** 상세에서 돌아오면 필터와 스크롤 위치를 복원해야 한다. 지금은 필터가 컴포넌트 상태라 돌아오면 초기화된다. 필터를 URL 쿼리로 옮기는 방식을 쓴다.
- **분석 취소.** 취소 후 늦게 도착한 응답으로 화면이 넘어가면 안 된다. 요청 중단(`AbortController`)과 응답 무시 처리가 필요하다.
- **데스크탑.** 같은 컴포넌트를 쓰되 `md` 이상에서 배치가 바뀐다(이력은 카드 → 테이블, 결과는 좌우 2단). 좁은 화면에서는 모바일 구성을 쓴다.

## 7. Storybook

공통 컴포넌트를 화면 없이 확인하고 문서로 남기는 곳이다. 지금 Button은 쓰는 화면이 없어 눈으로 확인하지 못했는데, 이 문제를 Storybook이 푼다.

**구성**

- `@storybook/nextjs-vite` 10.x. vitest와 같은 Vite 8을 쓰고(`vite`를 개발 의존성으로 명시), `next/link`·`usePathname`을 쓰는 컴포넌트도 올릴 수 있다.
- 애드온은 문서(`addon-docs`)와 접근성 검사(`addon-a11y`) 두 개로 시작한다.
- 미리보기에서 `globals.css`를 불러와 토큰·Pretendard·lucide 아이콘이 앱과 같게 보이게 한다.
- 툴바에 큰 글자 토글을 둔다. 앱과 같은 방식(`<html data-textsize="large">`)으로 적용해 모든 스토리를 100%와 125%로 바꿔 볼 수 있다.
- 스토리 파일은 컴포넌트 옆에 둔다(`Button.stories.tsx`). 앱 CSS에 스토리 전용 클래스가 섞이지 않게 앱의 Tailwind 스캔에서는 제외하고, Storybook 전용 Tailwind 설정에서만 스캔한다.
- 스크립트: `npm run storybook`(6006 포트), `npm run build-storybook`. `.next`를 쓰지 않아 dev 서버와 충돌하지 않는다. `frontend`에서 실행해야 Tailwind가 파일을 찾는다.
- `public` 폴더는 통째로 연결하지 않는다(오프라인 앱까지 딸려 온다). 마스코트·로고 같은 이미지가 필요한 스토리가 생기면 그 폴더만 `.storybook/main.ts`의 `staticDirs`로 연결한다.

**스토리 작성 규칙**

| 반드시 넣는 스토리 | 이유 |
|---|---|
| 변형마다 하나 (`variant` × `size`) | Figma 사양과 대조 |
| 상태마다 하나 (비활성, 진행 중, 선택됨, 펼침, 오류) | 화면에서 재현하기 어려운 상태 확인 |
| 긴 문구·두 줄 라벨 | 큰 글자 모드에서 잘리거나 겹치지 않는지 |
| 전체 모아보기 | 한 화면에서 일관성 확인 |

- 스토리 이름은 Figma 컴포넌트·변형 이름과 맞춘다.
- API나 라우트가 필요한 컴포넌트는 공통 컴포넌트가 아니다(3절 원칙 4). 기능 컴포넌트를 스토리로 올릴 때는 API 모듈을 가짜로 바꾼다.
- 스토리도 CI의 타입 검사와 lint 대상이다. 스토리가 깨지면 CI가 실패한다. `.storybook/`의 설정 파일은 타입 검사만 받고 lint는 받지 않으며, Storybook이 실제로 뜨는지는 CI가 확인하지 않는다.

**나중에 정할 것**: CI에 `build-storybook` 추가, 스토리를 테스트로 돌리는 애드온(`addon-vitest`), `eslint-plugin-storybook`. 스토리가 3~4개 모인 뒤 빌드 시간을 보고 정한다.

**작성 규칙**

- 역할과 이름으로 찾는다(`getByRole("button", { name: "다음" })`). 클래스 이름이나 DOM 구조로 찾지 않는다. 화면을 옮겨도 버튼 이름은 유지해서 기존 테스트가 그대로 통과해야 한다.
- 공통 컴포넌트는 Figma 사양표 테스트를 하나 둔다. 변형별로 어떤 토큰 클래스가 붙는지 고정해서, 디자인과 어긋나는 변경을 잡는다. 클래스 이름에 묶이지만 이 컴포넌트의 계약이 "Figma 토큰 대응"이라 감수한다.
- 동작이 있는 컴포넌트는 키보드 조작을 테스트한다: Dialog의 Esc와 초점 가두기, Accordion의 Enter·Space, Tabs의 선택 상태.
- 화면을 옮기는 PR은 옮기기 전에 그 화면의 현재 동작을 테스트로 먼저 고정한다. 테스트가 없는 화면(`/`, `/history/[id]`)이 대상이다.
- jsdom이 흉내 내지 못하는 것(실제 색 대비, 줄바꿈, 스크롤 고정)은 테스트로 보장하지 않고 Storybook과 실기기 확인으로 본다.
