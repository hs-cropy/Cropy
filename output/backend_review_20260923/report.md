# 백엔드 정밀 검토 — 2026-09-23

> 아래는 수정 전 분석 기록이다. 이후 반영한 우선 취약점 수정과 남은 범위는 [fixes.md](fixes.md)에 기록했다.

## 먼저 수정할 항목

### B01 · 높음 · 같은 농약의 작물/병해별 사용 조건이 소실됨

근거: [sync_pesticides.py](../../backend/scripts/sync_pesticides.py) 80–96, 123–130행; [entities.py](../../backend/app/models/entities.py) 31–56행; [diagnosis_service.py](../../backend/app/services/diagnosis_service.py) 21–32행.

동기화는 `pestiCode`로 농약을 합치고 처음 만난 조건만 저장한다. 희석배수·사용법·PHI·안전사용기준은 제품 테이블에 있으며 병해 매핑에는 priority만 있다. 따라서 같은 제품에 서로 다른 조건이 들어오면 나중 조건을 표현할 수 없다.

재현: 동일 제품 코드에 문맥 A의 PHI 3일, 문맥 B의 PHI 21일을 입력했다. 결과는 제품 1개, PHI 3일, 그 제품을 공유하는 매핑 2개였다. 실제 시드에도 `psis_721`이 무노균병·배추검은썩음병·배추노균병에 공유된다. 이 사실만으로 현재 해당 제품의 값이 틀렸다고 단정하지는 않는다. 현재 등록 조건은 별도 원천 대조가 필요하다.

수정: 제품 식별 정보와 작물/병해별 사용 조건을 분리한다. 단순한 시작점은 `DiseasePesticide`를 명시적인 사용 조건 엔티티로 바꾸는 것이다. 같은 제품·병해에도 여러 조건이 있으면 독립 usage ID가 필요하다. 이름 기반 upsert 대신 원천의 안정적인 제품/등록 식별자를 사용한다. 기존 데이터에서 유실된 조건은 스키마 이동만으로 복구되지 않으므로 원천 재수집이 필요하다.

완료 기준: 같은 제품의 상이한 조건 두 개가 동기화→DB→각 병해 API 응답까지 그대로 보존된다.

### B02 · 높음 · 파일명 확장자를 신뢰하여 검증된 이미지를 HTML로 제공

근거: diagnosis_service.py 43–46, 126–129행; [main.py](../../backend/app/main.py) 47행.

이미지 검증 후에도 사용자가 준 확장자를 보존하고 원본 바이트를 StaticFiles로 제공한다. 유효한 JPEG 뒤에 무해한 HTML 마커를 붙이고 `photo.html`로 업로드하면 진단 200, 파일 조회 200, `Content-Type: text/html`이며 HTML 마커도 남는다.

확인한 사실은 임의 확장자와 HTML 응답이다. 브라우저에서 스크립트 실행을 시연하지는 않았다. 프론트와 같은 출처로 제공되므로 활성 콘텐츠가 문서로 해석될 위험이 있다. UUID 파일명은 이 문제를 해결하지 않는다.

수정: 실제 검증된 이미지 포맷에서 서버가 확장자와 MIME을 결정한다. 허용 형식만 제공하고 `nosniff`를 보완적으로 적용한다. 필요하면 원본은 비공개 보존하고 화면용 이미지를 별도로 재인코딩한다. 재인코딩·EXIF 회전은 ML 입력 변화이므로 모델 담당과 전처리 계약을 맞춘다.

완료 기준: 유효한 이미지라도 `.html` 등 입력 파일명으로 HTML 응답을 만들 수 없고, 저장·응답 MIME이 실제 형식과 일치한다.

### B03 · 높음 · 알 수 없는 모델 클래스를 실제 병명으로 치환

근거: diagnosis_service.py 48–72행; ml_service.py 40–59, 134행.

예측 클래스와 DB가 전혀 맞지 않으면 `db.query(Disease).first()`를 사용한다. 모델 계약 오류가 정상적인 진단으로 바뀐다.

재현: `(class_id=999, confidence=0.99)`를 주입하면 **HTTP 200, 고추 탄저병, 0.99**를 저장·반환했다. 일부 클래스만 누락되면 매칭되는 하위 후보를 주 진단으로 올리므로 이 역시 계약 오류를 숨긴다.

수정: 임의 병해 fallback을 제거한다. 기동 시 모델 출력 차원·classes 길이·ID 유일성·지원 ID와 DB 매핑을 검증하고, 실행 시 빈/미등록/비정상 점수 분포를 명시적인 서비스 오류로 처리한다. 보조 모델도 2클래스와 허용 쌍 계약을 검증한다. 새 모델 클래스 정책은 모델 담당과 함께 정한다.

완료 기준: 불일치 모델은 준비 완료로 표시되지 않고 진단 행이나 잘못된 농약 추천을 생성하지 않는다.

### B04 · 높음 · PSIS 부분 실패를 정상적인 빈 목록처럼 반영

근거: sync_pesticides.py 41–62, 113–141행; [seed.py](../../backend/app/services/seed.py) 130–139행.

HTTP 상태만 확인하고 XML 업무 오류 코드를 검사하지 않는다. 한 병해라도 데이터가 있으면 전체 시드를 덮어쓴다. 재기동 시 시드에서 빠진 매핑은 삭제된다.

재현: 업무 오류 문구만 있는 HTTP 성공 XML이 `[]`로 파싱됐다. A·B 매핑이 있던 격리 시드에 A 결과와 B 빈 결과를 입력하자 동기화가 성공 종료하며 B 매핑을 제거했다. 실제 PSIS 오류 XML 스키마는 이 검사에서 조회하지 않았으므로 공식 계약에 맞춰 파서를 보완해야 한다.

추가 문제: JSON 두 개를 순차 덮어쓰므로 중간 실패 시 서로 다른 세대의 시드가 남을 수 있다. 첫 50건만 받고 최대 5개를 선택하므로 문서의 '목록에서 빠짐=등록 취소'라는 해석도 성립하지 않는다.

수정: 정상 0건과 조회 실패를 구분하고 모든 쿼리의 성공을 검증한 뒤 게시한다. 원천 응답·조회 조건·동기화 시각·스키마 버전을 보존한다. 시드를 버전 디렉터리에 함께 쓴 뒤 manifest/활성 버전을 교체하거나 단일 묶음으로 게시한다. 실패 시 기존 정상 버전을 유지한다. 전체 조회가 필요하면 페이징도 구현한다.

완료 기준: 한 쿼리의 업무 오류·잘못된 XML·중간 쓰기 실패가 기존 정상 시드를 바꾸지 않으며, 확인된 정상 0건만 명시적으로 반영된다.

### B05 · 운영 전 높음 · Mock과 모델 장애의 구분 부족

근거: [ml_service.py](../../backend/app/services/ml_service.py) 19, 29–60, 119–121행; health.py; docker-compose.yml.

모델 없음·로드 예외 모두 고정 샘플로 대체하고 원인을 로그에 남기지 않는다. 실제 진단 응답과 DB에는 모드가 없다. 재현에서도 `model_loaded=false`와 별개로 고추 탄저병 87%가 저장됐다. Compose healthcheck는 HTTP 성공만 확인한다. 실패 결과 None도 캐시되므로 파일을 나중에 배치해도 자동 재로드하지 않는다.

중요한 구분: PRD·API_SPEC·기존 테스트는 모델 없이 동작하는 Mock을 의도적으로 요구한다. 따라서 Mock 자체를 버그라고 판단하거나 개발 흐름을 일괄 제거해서는 안 된다.

수정: 시연 모드와 운영 모드를 명시적으로 나누고 응답/이력에 모드를 기록한다. 운영의 모델 장애는 503 등으로 표현한다. 생존 확인과 진단 준비 확인을 분리하고 readiness에 모델 계약 검증을 반영한다. 예외 로그와 재시작/재로드 정책도 명시한다.

완료 기준: 개발 Mock 테스트는 유지하되 운영 모드의 모델 누락/손상 테스트는 가짜 진단 생성을 거부한다.

## 동작·운영 안정성 수정

### B06 · 중간 · 선택 작물과 진단 작물의 의미가 혼합됨

근거: diagnosis 라우트의 자유 문자열 `crop_type`; diagnosis_service.py 86, 160–171행.

재현: `crop_type=unsupported`도 수용했고 `무` 선택 시 `고추 탄저병`이 함께 반환됐다. 재촬영에서 병해를 배추 정상으로 변경해도 crop_type은 무로 남았다.

API_SPEC은 crop_type을 사용자 선택값으로 정의하므로 '선택 작물을 추론에 강제로 적용하지 않았다' 자체는 명세 위반이 아니다. 문제는 잘못된 값도 받으며 사용자 선택과 예측 작물을 한 필드로 표현한다는 것이다.

수정: 허용 작물 enum, `selected_crop`/`predicted_crop`와 불일치 상태를 정의한다. 기존 crop_type의 의미를 유지할지 바꿀지 API 계약에서 결정한다. 무조건 다른 작물 점수를 제거하거나 재정규화하면 점수 의미가 바뀌므로 별도 모델 검증 없이 적용하지 않는다.

완료 기준: 미지원 값은 422이고, 최초 진단과 재촬영 모두 작물 불일치를 소비자가 식별할 수 있다.

### B07 · 중간 · async 라우트의 동기 추론이 이벤트 루프를 막음

근거: [diagnosis.py](../../backend/app/api/routes/diagnosis.py) 54–77행.

파일을 읽은 뒤 동기 추론·파일 쓰기·동기 DB 작업을 async 함수에서 직접 호출한다. 단일 워커가 기본인 배포 구조와 맞물린다.

재현: 동기 추론에 0.3초 지연을 주입하자 같은 이벤트 루프의 0.02초 타이머가 약 0.325초 뒤 실행됐다. 이는 실제 모델 지연 실측이 아니라 블로킹 구조의 재현이다.

수정: 동기 작업을 제한된 스레드풀 또는 별도 실행 경로로 이동한다. DB 세션은 한 작업 단위에서 생성·사용·종료하고 동시 공유하지 않는다. 모델 병렬 실행 수를 제한하여 메모리 사용과 대기 요청을 관리한다. 처음부터 분산 작업 큐를 도입할 필요는 없다.

완료 기준: 긴 추론 중 health/다른 요청이 진행되고, 동시에 들어온 추론의 자원 사용과 타임아웃이 통제된다.

### B08 · 중간 · 업로드 상한이 요청 수신 자체를 제한하지 못함

근거: diagnosis.py 18–40행; 설치된 FastAPI routing.py의 `await request.form()`; Starlette formparsers.py의 multipart 스트림 전체 파싱.

재현: 1MB 제한, 약 2MB 요청을 ASGI 청크로 전달했을 때 **2,097,289바이트 전체가 수신된 뒤** `_read_image_upload`가 호출되고 413을 반환했다. 현재 제한은 파싱된 UploadFile을 다시 읽는 단계의 제한이다. 문서의 '요청을 전부 읽기 전에 중단' 설명은 실제와 다르다.

수정: 배포 프록시 또는 ASGI 수신 계층에서 전체 요청 바이트 제한을 적용하고, Content-Length가 없는 요청도 처리한다. 전체 multipart 한도와 개별 파일 한도를 구분한다. 현재 앱 내부 제한도 유지한다.

완료 기준: 한도 초과 청크 요청을 끝까지 수신/임시 저장하지 않고 중단한다. 프론트 프록시 경유와 백엔드 직접 호출을 모두 확인한다.

### B09 · 중간 · 이미지 verify 통과 후 디코딩 실패가 500이 됨

근거: diagnosis.py 45–48행; ml_service.py 128, 155행.

재현: JPEG의 마지막 20바이트를 제거한 파일이 `verify()`를 통과했지만 RGB 디코딩에서 실패하여 500이 됐다. Pillow 픽셀 제한을 낮춰 작은 이미지로 검사한 경우도 DecompressionBombError가 처리되지 않아 500이었다. 실제 대형 이미지는 만들지 않았다.

수정: 디코딩 성공 여부와 가로·세로/총 픽셀 한도를 확인하고 예상 이미지 오류를 400/413 등 정해진 응답으로 변환한다. 포맷/MIME 처리(B02)와 한 경계에서 검증해 반복 디코딩 비용도 줄인다.

완료 기준: 손상 헤더뿐 아니라 손상 픽셀 데이터, 픽셀 한도 초과, 비지원 형식 테스트가 통과한다.

### B10 · 중간 · 실패·반복 재촬영 시 고아 파일 누적

근거: diagnosis_service.py 46–48, 129–132, 164행.

재현: 추론 예외를 주입하면 500 후 파일 1개가 남는다. 같은 진단을 두 번 재촬영하면 DB가 새 경로로 덮이지만 이전 재촬영 URL도 200으로 제공된다. 일반 보존 기한 정리 부재는 이미 ARCHITECTURE에 기록돼 있다.

수정: 요청 단위로 새로 만든 파일을 추적하고 저장 실패 시 정리한다. DB 반영 성공 후 참조가 사라진 파일을 정리하거나 별도 촬영 이력으로 보존한다. 데이터 보존 정책과 실패 보상을 구분한다.

완료 기준: 추론/DB 실패 및 반복 재촬영 후 DB와 파일 참조 관계가 일치한다. 운영 파일을 대상으로 한 무차별 삭제 테스트는 하지 않는다.

### B11 · 중간 · SQLite 시간대 정보가 API에서 소실됨

근거: entities.py 70행; 프론트 history/page.tsx 67행; API_SPEC의 Z가 포함된 시간 예시.

재현 응답은 `2026-09-23T12:39:53`처럼 Z/offset이 없었다. `DateTime(timezone=True)` 선언만으로 현재 SQLite 응답에 시간대가 붙지 않는다. 프론트는 이를 `new Date(...)`로 해석하므로 UTC로 생성된 값을 한국 로컬 시간으로 오인할 수 있다.

수정: UTC 저장/조회/직렬화 정책을 정하고 응답에 Z 또는 명시적 offset을 제공한다. 기존 naive 데이터의 실제 생성 기준을 확인한 뒤 보정한다. 이미 로컬 시각인 데이터에 무조건 UTC를 붙이면 안 된다.

완료 기준: UTC·Asia/Seoul 환경에서 같은 이벤트를 같은 순간으로 표시한다.

### B12 · 중간 · 농약 추천 priority가 응답 순서에 반영되지 않음

근거: entities.py의 secondary relationship; diagnosis_service.py의 `disease.pesticides` 순회; DATABASE의 '낮을수록 우선 추천'.

재현: 격리 DB의 첫 매핑 priority를 99, 마지막을 0으로 바꿨지만 응답 첫 농약은 바뀌지 않았다. 기존 테스트는 priority 값의 갱신만 확인한다.

수정: 사용 조건/매핑을 명시적으로 조회하면서 priority와 안정적인 보조 키로 정렬한다. B01의 모델링 변경에 포함하면 중복 작업을 줄일 수 있다.

완료 기준: 최초 진단·재촬영·병해 상세·이력 상세 모두 같은 추천 순서를 반환한다.

### B13 · 보드 이전 전 중간 · DB에 저장한 OS/배포 경로를 그대로 재사용

근거: diagnosis_service.py 35–38, 85, 121행; Orange Pi 배포 문서의 DB와 uploads 함께 이전 절차.

코드는 로컬 `Path` 문자열을 저장한다. Windows에서 생성한 `uploads\\...`를 Linux의 Path에 넣거나 네이티브 경로를 Compose의 `/data/uploads`로 옮기면 경로 의미가 달라진다. URL basename 추출도 Windows 경로를 Linux에서 해석할 때 깨질 수 있다. 이 항목은 코드 추적으로 확인한 이전 위험이며 Linux 보드에서 재현하지 않았다.

수정: DB에는 저장 루트에 독립적인 파일 키를 저장하고 현재 upload_dir에서 해석한다. 기존 경로 마이그레이션과 백업 복원 검사를 제공한다.

완료 기준: Windows/네이티브에서 만든 이력을 Linux/Compose로 이전한 뒤 원본·재촬영 이미지 조회와 refine가 동작한다.

## 명세를 정한 뒤 진행할 개선

### 재촬영 상태와 모델 추적

- 재현에서 최초 응답에는 recapture가 있었지만 이력 상세에는 없었다. API_SPEC도 이력에서는 미제공으로 정의한다. 따라서 단순 누락 버그가 아니라, 화면 이탈 후 재촬영을 이어갈 수 있게 할지 결정할 UX/API 개선이다.
- DB에는 모델 버전·전체 최초 분포·최초/최종 결과 구분이 없다. refine는 현재 모델로 원본을 재추론한다. 배포 간 모델 변경이 있으면 최초 조건과 달라지므로 모델 해시·전처리 버전·원본 분포와 수정 시각을 보존하는 것이 적절하다.
- 재촬영 API는 최초 안내가 없던 진단이나 이미 재촬영한 진단도 받는다. 기존 API 테스트도 이를 허용한다. 갑자기 409를 도입하기보다 재촬영 자격·반복 정책을 명세화한다.
- 보조 분류기는 파일이 있으면 자동 적용되지만 MODEL_SPEC에 효과 미확인과 학습/서빙 도메인 차이가 명시돼 있다. 명시적 enable 설정과 모델 식별자, 적용 여부 기록을 두고 검증된 경우 활성화하는 것이 적절하다. 새 기준선과 구 보조 모델 조합의 유효성은 별도 ML 평가다.
- Qwen 연결 전 `prediction_mode`, 모델 점수의 의미, `severity`가 병해 DB 속성이라는 점, 농약 데이터 출처/검증 시점/조회 실패 상태를 API에 표현해야 한다. 현재 빈 pesticides 배열만으로 정상·등록 정보 없음·동기화 실패를 구분할 수 없다.

### DB 무결성과 운영

- 격리 DB에서 `PRAGMA foreign_keys=0`이었다. FK 선언만으로 현재 연결에서 강제되지 않는다. 기존 고아 참조 감사 후 연결별 FK 활성화와 rollback 테스트를 추가한다. 현재 운영 DB의 무결성 손상을 발견했다는 의미는 아니다.
- DATABASE/ARCHITECTURE는 PostgreSQL 운영을 상정하지만 `check_same_thread=False`가 무조건 전달되고 드라이버도 requirements에 없다. 현재 목표인 단일 보드 SQLite를 유지한다면 문서를 먼저 맞추고, PostgreSQL 이전은 실제 필요가 생겼을 때 dialect별 설정·마이그레이션과 함께 진행한다.
- DB 형태 변경(B01 등)에는 현재 ADD COLUMN 목록만으로 부족할 수 있다. 데이터 이전·rollback·백업 검증이 있는 마이그레이션을 준비한다.
- `torch.load(weights_only=False)`는 관리자가 배치한 체크포인트를 읽는 경로이며 원격 업로드 모델 기능은 없다. 즉 현재 원격 모델 업로드 취약점으로 확대 해석하지 않는다. 실제 기존 체크포인트 호환성을 확인한 뒤 weights_only=True와 해시 확인으로 좁히는 것은 합리적이다.
- 모든 이력·이미지에 인증이 없다는 점은 문서의 Phase 2 범위다. 다중 사용자 공개 배포 전에는 소유권·이미지 접근 제어가 필요하지만 단일 사용자 로컬 데모의 즉시 구현 결함으로 분류하지 않았다.
