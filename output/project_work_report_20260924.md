# cropy 프로젝트 전체 작업 보고서

- 작성일: 2026-09-24
- 대상: 프로젝트 문서·백엔드·프론트엔드 연동·ResNet50 학습 결과
- 범위: 이번 대화에서 수행한 분석, 코드 수정, 실행 검증 및 결과 해석
- 상태: 주요 백엔드 개선과 프론트엔드 연동을 구현하고 로컬 테스트·빌드를 확인했다. 운영 배포와 실데이터 전환은 수행하지 않았다.

## 1. 작업 목적과 주요 결과

프로젝트 전체 문서와 구현을 대조하여 백엔드에서 우선 수정해야 할 문제를 찾고, 취약도가 높은 항목부터 개선했다. 이후 사용자가 제공한 256 입력 학습 결과를 기존 224 기준선과 비교했다.

주요 결과는 다음과 같다.

1. 업로드 파일이 HTML 등으로 제공될 수 있는 문제와 손상·과대 이미지 처리 문제를 보완했다.
2. 잘못된 모델 출력을 실제 병명으로 바꾸던 처리를 제거하고, 운영 환경에서 예시 진단을 반환하지 않도록 했다.
3. 농약 제품과 작물·병해별 사용 조건을 분리하고, 미검증 사용 조건의 노출과 동기화 부분 실패에 따른 데이터 손상을 방지했다.
4. 진단·재촬영의 DB 및 파일 처리, 이력 재현성, 동시 수정 충돌, 요청 제한을 개선했다.
5. 프론트엔드에 예시 결과·작물 불일치·미검증 농약 안내를 연결했다.
6. 최종 백엔드 테스트는 **183개 통과, 1개 제외**였으며 프론트엔드 프로덕션 빌드도 성공했다.
7. 새 ResNet50 256 실험은 검증 정확도 **92.48%**로 기존보다 **0.64%p** 높았지만, 무 병해 간 혼동은 증가했다. 서비스 모델은 교체하지 않았다.

### 2.1 검토 범위

### 2.2 수행 방법

코드와 문서 대조, 임시 DB·업로드 경로를 사용하는 결함 재현, 회귀 테스트, 통합 테스트, 프론트엔드 빌드 검증을 수행했다. 모델 실패와 PSIS 오류는 필요한 경우 테스트에서 주입했다. 이는 서비스 로직 검증이며 실제 PSIS 등록 정보나 현장 모델 정확도의 검증을 대신하지 않는다.

디버깅·테스트 주도 개발·병렬 검토·완료 전 검증 및 React 검토 스킬을 활용했다. PSIS 연동 조건은 공식 안내를 참고했다. 별도의 신규 플러그인 설치는 하지 않았다.

기존 작업 트리의 사용자 변경은 보존했다. 저장소 전체 변경 목록에는 기존 작업도 섞여 있으므로, 모든 변경을 이번 작업의 성과로 계산하지 않았다.

## 4. 주요 구현 상세

### 4.1 업로드와 요청 처리

- 허용 이미지 형식은 JPEG와 PNG로 제한했다.
- 입력 파일명이 아닌 실제 이미지 형식으로 저장 확장자를 결정한다.
- 이미지 제공 시 MIME을 고정하고 `X-Content-Type-Options: nosniff`를 적용한다.
- 이미지 구조 검사 후 전체 픽셀 디코딩을 확인한다. 손상 데이터는 400, 용량·픽셀 제한 초과는 413으로 처리한다.
- 기본 픽셀 상한은 40,000,000이다.
- 전체 HTTP 본문은 파일 용량 제한에 64 KiB를 더한 한도로 multipart 해석 전에 검사한다. Content-Length가 없거나 실제 크기와 달라도 수신 바이트를 계산한다.
- 작은 요청은 메모리, 큰 요청은 임시 디스크를 사용한다. 배포 시 임시 공간과 프록시의 느린 업로드 제한은 별도로 관리해야 한다.

### 4.2 모델 신뢰성과 실행 모드

- 빈 출력, 중복·비정수 클래스 ID, 범위 밖·비유한 점수, DB 미등록 클래스 및 재촬영 클래스 집합 불일치를 차단한다.
- 체크포인트 구조, 허용 모델 종류, 클래스 수, 입력 크기 및 가중치의 유한성을 검사한다.
- 체크포인트는 `weights_only=True`로 읽는다.
- 모델 해시, 전처리 버전, 예측 모드를 진단에 기록한다.
- 개발에서 허용한 경우에만 mock을 제공한다. 운영에서 모델을 사용할 수 없으면 진단은 503이다.
- `/api/v1/health`는 프로세스 생존, `/api/v1/ready`는 실제 모델과 DB 매핑의 준비 상태를 나타낸다. mock은 ready가 503이다.
- 선택적 pair 모델은 명시적으로 활성화할 때 사용한다.

### 4.3 진단·재촬영·이력

- 선택한 작물과 모델이 예측한 작물을 구분하고 불일치를 반환한다.
- 원본의 전체 예측 분포를 저장하여 재촬영 결합에 활용한다. 기존 이력에 저장 분포가 없으면 호환 경로로 원본을 다시 추론한다.
- 본 모델·전처리·예측 모드가 달라진 상태의 재촬영 결합은 409로 차단한다.
- DB revision으로 동시 수정 충돌을 감지하고 409로 처리한다.
- 실패 시 DB를 롤백하고 해당 요청에서 생성한 파일을 제거한다. 기존 결과는 보존한다.
- 재촬영 저장이 커밋된 뒤 이전 재촬영 파일을 제거한다.
- 재촬영 안내를 이력에 보존하고 상세 화면에서 다시 사용할 수 있게 했다.
- 작물별 이력 조회와 재촬영 이미지 정보를 응답에 연결했다.

### 4.4 농약 데이터

- 제품 식별 정보와 작물·병해별 희석비·사용법·안전기간을 분리했다.
- 사용 조건마다 식별자, 출처, 동기화 시간, 검증 상태와 원천 레코드를 저장한다.
- 기존 시드는 제품명을 유지하되 검증되지 않은 수치·사용 조건을 숨긴다. DB 구조 변경만으로 과거에 유실된 조건이 복구되지는 않는다.
- PSIS 페이지 누락, 업무 오류, 잘못된 응답 및 식별자 충돌을 검증한다.
- 모든 조회 성공 후 `pesticide_catalog.json`을 원자적으로 교체한다. DB 반영도 트랜잭션으로 처리한다.
- 실제 최신 등록 조건 확인을 위해서는 별도의 승인된 키를 이용한 실데이터 동기화와 원천 확인이 필요하다. 이번 작업에서 실동기화는 실행하지 않았다.

### 4.5 DB와 파일 운영

- SQLite 외래 키 검사를 활성화했다.
- 기존 DB에 칼럼을 추가할 때 무결성을 확인하고 SQLite 백업을 만든 뒤 트랜잭션으로 변경한다.
- 무결성 위반 데이터를 임의로 삭제·보정하지 않는다.
- 신규 이력에는 운영체제 경로 대신 파일 키를 저장한다. 과거 Windows 경로는 파일명 기준으로 호환한다.
- 고아 업로드 정리 CLI를 추가했다. 기본은 미리보기이며, `--apply`를 명시해야 삭제한다.
- 정리 대상은 오래된 미참조 일반 파일이다. DB 참조 파일, 하위 폴더와 심볼릭 링크는 제외한다. 실제 삭제는 서비스를 정지한 유지보수 시간에 실행하도록 운영 문서에 명시했다.

## 5. 프론트엔드 및 문서 반영

### 5.1 프론트엔드

- API 타입에 모델 출처·버전, 선택·예측 작물, 농약 검증 정보를 반영했다.
- mock 진단을 실제 진단과 구분하는 안내를 추가했다.
- 선택 작물과 예측 작물이 다르면 확인 메시지를 표시한다.
- 정상 결과를 확정적으로 표현하지 않도록 문구를 조정하고, 낮은 분류 점수에 대한 안내를 정상 클래스에도 적용했다.
- 미검증 농약의 사용 조건이 표시되지 않는 이유를 안내한다.
- 이력 상세에서 저장된 재촬영 안내와 갱신 결과를 연결했다.

### 5.2 문서·배포 설정

README, API_SPEC, DATABASE, ARCHITECTURE 및 Orange Pi 배포 안내의 관련 내용을 수정했다. 환경변수 예시와 Compose에 개발·운영 모드, pair 모델, 동시 진단 설정을 반영하고 readiness 경로를 healthcheck에 연결했다.

신규 [백엔드 운영 문서](https://github.com/hs-cropy/Cropy/blob/backend/docs/BACKEND_OPERATIONS.md)에 모델 준비 상태, DB 백업·복구, PSIS 카탈로그 갱신, 업로드 정리 및 요청 제한 운영 절차를 기록했다. 후속 기획 문서의 모든 기능을 구현한 것은 아니다.

## 6. 실행 검증

| 단계 | 결과 | 의미 |
|---|---|---|
| 수정 전 백엔드 기존 테스트 | 27 passed | 초기 기준선 |
| 1차 수정 후 전체 테스트 | 74 passed | 업로드 및 예측 계약 보완 검증 |
| 최종 백엔드 전체 테스트 | **183 passed, 1 skipped**, 30.76초 | 농약·모델·요청 제한·DB·이력·파일 처리 통합 검증 |
| 프론트엔드 타입 검사 | 통과 | API 타입 및 화면 연결 확인 |
| 프론트엔드 프로덕션 빌드 | 성공 | 컴파일, lint·타입 검사, 정적 페이지 생성 확인 |

최종 백엔드 실행 명령은 backend 디렉터리에서 `.venv\Scripts\python.exe -m pytest -q`, 프론트엔드는 frontend 디렉터리에서 `npm.cmd run build`였다. 위 수치는 앞서 실제 실행한 검증 기록이며, 이 보고서 작성만을 위해 다시 실행한 값은 아니다.

Windows에서 심볼릭 링크 생성 권한이 없어 관련 테스트 1개가 제외됐다. pytest 캐시 디렉터리 쓰기 경고 1개가 있었으나 테스트 실행은 성공했다. 전체 브라우저 사용자 흐름과 실장치 검증은 수행하지 않았다.

추가된 주요 회귀 테스트는 다음과 같다.

- `test_upload_security.py`, `test_prediction_validation.py`
- `test_model_lifecycle.py`, `test_diagnosis_integrity.py`
- `test_request_limits.py`, `test_database_migration.py`
- `test_pesticide_catalog.py`, `test_cleanup_uploads.py`

## 7. ResNet50 학습 결과 분석

### 7.1 실험 조건과 검증

사용자가 제공한 `cropy_group256_results_20260923_104105_054987.zip`을 기존 224 입력 실험과 비교했다. 두 실험은 ResNet50, ImageNet V2 초기화, seed 42, batch 32, 20 epoch이며 같은 작업자 분리 manifest를 사용했다.

ZIP CRC, manifest SHA256, 검증 예측 785개의 경로·정답, 혼동행렬, 정확도·Macro F1 재계산, epoch 기록 및 최고 모델 선택을 확인했다. 체크포인트 메타데이터와 가중치의 유한성도 확인했다. 전체 이미지 로컬 재추론과 test 평가는 하지 않았다.

### 7.3 파인튜닝 여부와 해석

[학습 코드](../ml/train_group_baseline.py)는 ImageNet으로 사전학습한 ResNet50 V2를 불러와 마지막 분류층을 9개 클래스로 바꾸고, `model.parameters()` 전체를 optimizer에 전달한다. 따라서 현재 결과는 이미 **ResNet50 전체 파인튜닝 결과**다. ResNet50을 새로 도입해야 하는 상태가 아니다.

추가 학습으로 개선될 가능성은 있지만 보장할 수 없다. 학습 정확도 100%와 검증 정확도 92.48%의 차이, 무 병해 혼동을 고려하면 epoch만 늘리는 것보다 원본 오류 검토와 촬영 환경 다양성 확보가 우선이다. 학습·평가의 측정 조건도 달라 정확도 차이만으로 원인을 확정하지 않는다.

단일 seed 결과이므로 안정적인 우위를 확정하지 않는다. 작업자 분리는 개체·농장 독립성을 보장하지 않으며, 무노균병 검증 표본은 작업자 1명의 49장이다. 반복적인 val 기반 실험 선택의 영향을 고려해 최종 후보 확정 후 별도 test 평가가 필요하다.

256 모델은 후보로 보존했다. 서비스 모델 교체, 신뢰도 임계값 변경, pair 모델 활성화는 이번 결과만으로 수행하지 않았다.

## 9. 적용 범위와 제한

- 실제 운영 DB, 서비스 체크포인트 및 실제 농약 시드는 이번 수정 과정에서 교체하지 않았다.
- 코드와 테스트 및 문서를 수정했으며 배포·커밋·푸시는 하지 않았다.
- 구형 GIF/WebP 등 비허용 확장자 이미지 이력의 별도 이전은 수행하지 않았다.
- 테스트 통과는 현장 진단 정확도, PSIS 정보의 현재성 또는 실장치 성능을 보장하지 않는다.
- 최신 학습 산출물의 구조·수치는 검증했지만 모델의 현장 적용 적합성은 별도 평가 대상이다.
