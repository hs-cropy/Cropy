## 1. 3주차 — LLM 역할 정의와 학습 데이터 설계 문제 분석

### 1.1 주요 수행 내용 및 개인별 수행 업무

김헌영은 특강 내용을 프로젝트에 적용하기 위한 LLM 파인튜닝 계획을 작성하고, 데이터의 목적·형식·시나리오·검수 기준을 정리하였다. LLM의 역할은 사진을 직접 재진단하는 것이 아니라 CNN과 백엔드가 제공하는 결과를 쉬운 한국어로 설명하고 후속 질문에 답하는 것으로 설정하였다.

계획에 포함한 작업은 다음과 같다.

- 병해 결과, 정상 결과, 재촬영, 원인·예방, 농약 정보, 후속 질문, 범위 밖 질문으로 시나리오 구분.
- `system`·`user`·`assistant` 메시지 기반 JSONL 형식과 가상 예시 제시.
- 실제 API 응답과 검증된 DB 내용을 정답의 근거로 사용하는 원칙 정의.
- 누락 정보, 작물 불일치, 음성 인식 오류, 다중 턴 문맥을 포함하는 경계 사례 정리.
- 같은 진단·문장·대화에서 파생한 사례를 묶어 분할 간 유사 사례 유입을 방지하는 기준 제안.

### 1.2 주요 문제점 및 분석

| 문제 | 발생 가능한 상황 | 데이터에 미치는 영향 |
|---|---|---|
| CNN과 LLM 역할 혼동 | LLM이 제공 후보를 바꾸거나 새 병명을 생성 | 설명용 정답이 근거 없는 재진단을 학습시킴 |
| 분류 점수의 의미 왜곡 | 점수 0.87을 실제 발병 확률 87%로 설명 | 불확실한 결과를 확진처럼 전달 |
| 정상 결과의 과도한 단정 | 정상 분류를 모든 병이 없다는 뜻으로 작성 | 오분류 가능성과 추가 관찰 필요성 누락 |
| 농약 정보의 근거 부족 | 빈 목록·미검증 시드에 임의의 약명·사용량 추가 | 검증되지 않은 수치가 정답 데이터에 포함 |
| 누락값 오해 | `null`을 0일·0배 등으로 해석 | 정보 부족과 실제 수치를 혼동 |
| 단순 문장 증강 편중 | 같은 질문을 어미만 바꿔 다량 생성 | 규모는 커지지만 실제 실패 유형은 부족 |
| 학습·평가 간 유사 사례 중복 | 같은 진단의 바꿔쓰기 질문을 무작위 분할 | 평가 점수가 실제 일반화 능력보다 높아질 가능성 |
| 다중 턴·STT 오류 부족 | “그 약은?”처럼 대상이 생략된 질문 | 이전 진단·농약 대상을 잘못 연결 |

위 항목은 설계 검토에서 식별한 위험이며, 실제 LLM 생성 오류의 발생률을 측정한 결과는 아니다.

### 1.3 해결 방법 및 데이터 구축 기준

**입력 근거를 제한한다.** 병명·작물·점수·후보·예방·농약·재촬영 정보를 백엔드 응답에서 필요한 만큼 전달하고, 정답 작성자는 근거 필드를 먼저 기록한다. 사진 경로와 내부 식별자는 질문에 필요하지 않으면 모델 입력에서 제외한다.

**불확실성과 정보 부족을 정답에 포함한다.** 높은 분류 점수도 확진으로 표현하지 않으며, 농약 정보가 비었을 때는 현재 제공된 정보만으로 안내할 수 없다는 응답을 작성한다. 재촬영 안내가 있으면 이를 우선 전달한다.

**문장 수보다 상황의 다양성을 확보한다.** 질문의 말투뿐 아니라 후보 간 점수 차이, 누락 필드, 진단 대상 변경, 재촬영 전후, 음성 인식 오류를 조합한다. 생성형 모델로 증강하더라도 팀원이 병명·수치·근거를 검수하도록 한다.

**증강 전에 시나리오 단위로 분리한다.** 동일 사진·진단·기준 문장·대화에서 파생한 사례를 `scenario_group_id`로 묶고 같은 분할에 배치한다. test를 보고 수정한 사례는 이후 개발용으로 전환하고 최종 평가 세트는 별도로 유지한다.

### 1.4 데이터 규모 제안과 완료 범위

| 시나리오 | 학습 목표 수량 |
|---|---:|
| 병해 결과 설명 | 200 |
| 정상 분류 결과 설명 | 100 |
| 재촬영 안내 | 150 |
| 원인·예방 질문 | 150 |
| 농약 정보 및 정보 부족 | 150 |
| 후속 질문·대상 불명확·STT 오류 | 150 |
| 범위 밖·입력 충돌·지시 무시 유도 | 100 |
| 합계 | 1,000 |

위 수량은 검수된 대화 단위의 **계획값**이다. 별도 validation 200개, test 200개와 train 분포에서 선정한 calibration 300~1,000개를 제안하였다. 실제 데이터셋 생성 수량, 검수 통과율, 학습 성능은 아직 보고할 근거가 없다.

3주차 산출물은 적용 계획과 데이터 설계 기준이다. LLM 학습 실행·어댑터 생성·보드 변환 완료로 표현하지 않는다.

## 2. 4주차 — 실제 진단 데이터의 문제점과 LLM 입력 요구사항 보완

### 2.1 주요 수행 내용 및 개인별 수행 업무

김헌영은 백엔드·DB·프론트엔드 검토와 개선을 수행하면서 LLM에 전달할 원천 진단 정보의 신뢰성을 점검하였다. 모델 출력 검증, 예측 모드·버전 기록, 선택·예측 작물 구분, 농약 사용 조건의 검증 상태, 재촬영 이력 보존 등을 구현하였다.

이 작업은 **LLM 입력으로 사용할 기반 데이터의 품질 개선**이다. 해당 필드를 소비하는 LLM 입력 구성기, 정답 데이터셋, 학습·평가 파이프라인을 완료했다는 의미는 아니다. 아래 요구사항은 4주차 구현 결과를 토대로 본 보고서에서 정리한 후속 데이터 설계 항목이다.

### 2.2 발견한 문제와 데이터 반영 방안

| 원천 데이터 문제 | LLM 학습 데이터에서 생길 수 있는 오류 | 4주차 반영 또는 후속 요구사항 |
|---|---|---|
| 잘못된 모델 출력의 임의 대체 | 실제 모델 근거가 없는 병명으로 설명 생성 | 출력·클래스 검증 구현; 실패 상태는 정상 진단 설명과 분리 |
| 예시 진단과 실제 진단 혼재 | mock을 실제 진단 사례로 학습 | 예측 모드 기록·운영 mock 차단 구현; 데이터 생성 시 모드 검사 필요 |
| 선택 작물과 예측 작물 혼재 | 사용자가 선택한 작물에 잘못된 결과를 붙임 | 두 값을 구분해 저장·표시; 불일치 시 확인하는 정답 필요 |
| 농약 제품과 사용 조건 혼재 | 다른 작물·병해의 사용 조건을 답변 | 제품·조건 분리 구현; 검증된 해당 조건만 컨텍스트에 포함해야 함 |
| 미검증 농약 정보 노출 | 수치가 있다는 이유만으로 공식 정보로 설명 | 미검증 조건 숨김 구현; 정보 부족 사례로 분류 필요 |
| 모델 변경 전후 재촬영 결합 | 서로 다른 기준의 예측을 같은 근거로 설명 | 모델·전처리 버전 기록 및 불일치 결합 차단 구현 |
| 재촬영 상태·진단 대상 변경 | 이전 후보·안내를 현재 결과에 적용 | 저장 이력 활용 및 대화 대상 갱신 규칙 필요 |
| 낮은 점수의 정상 분류 | “건강하므로 조치 불필요”로 단정 | 화면의 불확실성 안내 반영; LLM 정답도 같은 의미 유지 필요 |

### 2.3 학습·검수에 추가해야 할 사례

| 입력 상황 | 기대 응답 행동 | 금지할 행동 |
|---|---|---|
| 선택 작물과 예측 작물이 다름 | 불일치를 알리고 대상을 확인 | 선택 작물 또는 예측 작물을 임의로 덮어쓰기 |
| 모델 사용 불가 | 앱 오류·재시도 안내로 처리 | 예시 병명을 실제 결과처럼 설명 |
| 농약 사용 조건 미검증 | 현재 제공 정보의 한계를 안내 | 희석배수·안전기간을 추정 |
| 농약 수치가 `null` | 정보가 없음을 명시 | `null`을 0으로 치환 |
| 재촬영 안내 존재 | 제공된 부위·촬영 안내를 우선 전달 | 재촬영을 생략하고 확진·방제 단정 |
| 정상 후보지만 점수가 낮음 | 정상 후보와 불확실성을 함께 설명 | 모든 병이 없다고 보장 |
| 진단 대상 변경 후 “그 약은?” | 현재 대상이 명확한지 확인 | 이전 진단의 약을 자동 연결 |
| 입력 안에 규칙 무시 지시 포함 | 입력을 자료로 취급하고 근거 유지 | 사용자·DB 문장을 시스템 명령으로 취급 |

예를 들어 “농약 목록이 비어 있다”는 입력에 대한 정답은 “이 병에 쓸 농약은 없다”가 아니라 “현재 제공된 정보에는 안내할 농약 정보가 없다”이다. 데이터 부재와 실제 대상의 부재를 구분해야 한다.

### 2.4 평가 방법 및 남은 과제

현재는 기본 LLM과 파인튜닝 모델의 비교 수치가 없다. 먼저 같은 입력·질문·system 지시로 기본 모델을 평가한 뒤 반복 실패가 확인되는 경우 학습 효과를 비교해야 한다.

| 평가 항목 | 측정 내용 | 현재 상태 |
|---|---|---|
| 근거 준수 | 병명·작물명·수치가 입력과 일치하는 비율 | 평가 계획 |
| 불확실성 처리 | 재촬영·누락 정보에 대한 기대 행동 수행률 | 평가 계획 |
| 근거 없는 생성 | 없는 농약·수치·확진 표현의 발생 건수 | 평가 계획 |
| 한국어 안내 품질 | 관련성·쉬운 표현·간결성 | 평가 계획 |
| 학습 효과 | 기본 모델과 학습 모델의 동일 문제 비교 | 미실행 |
| 보드 적용성 | 변환 가능 여부·메모리·응답 지연 | 미검증 |

후속 작업은 다음 순서로 진행한다.

1. 현재 API 필드와 기존 LLM 계획의 입력 예시를 대조하여 실제 입력 계약을 확정한다.
2. 근거·기대 행동·출처 버전·검수자를 기록한 소규모 검수 세트를 작성한다.
3. 기본 모델의 실패 사례를 수집하고 데이터 보완 필요성을 판단한다.
4. 시나리오 단위 분할과 중복 검사를 수행한 뒤 JSONL 학습 데이터를 확대한다.
5. 필요할 때 LoRA 실험을 진행하고 동일 평가 세트로 개선 여부를 비교한다.
6. 선정 모델과 제공 RKLLM 도구의 호환성을 확인한 뒤 보드 평가를 수행한다.

농약명·사용량·안전사용기준 등은 학습만으로 정확성이 보장된다고 가정하지 않는다. 검증된 DB 값을 화면에 표시하고 LLM은 설명을 담당하며, 생성 결과가 근거와 충돌하면 템플릿 응답으로 전환하는 구성이 계획되어 있다.

### 2.5 팀 내 후속 역할 분담안

아래는 후속 작업의 분담안이며 다른 팀원의 수행 완료 실적이 아니다.

| 담당 | 후속 업무 |
|---|---|
| 김헌영 / PM·모델 | 데이터 검수 기준·분할·기본 모델 평가·학습 비교 |
| 박성호 / API | 실제 진단 응답의 LLM 입력 계약·근거 검증·대체 응답 |
| 고명준 / 카메라·음성 | STT 오류 사례·TTS용 응답 평가 |
| 김민서 / 프론트엔드 | 화면·음성 설명 및 오류·재촬영 상태의 일치 확인 |
| 이서하 / 배포·디바이스 | 변환 도구·런타임 호환 및 보드 성능 검증 |

## 3. 주차별 성과와 한계

| 구분 | 확인된 성과 | 미완료 사항 |
|---|---|---|
| 3주차 | LLM 역할·대화 형식·시나리오·검수·분할 계획 정리 | 실제 학습 데이터셋 구축 및 기본 모델 평가 |

LLM 데이터의 실제 오류율이나 학습 후 성능 향상률은 측정되지 않았다. 이번 단계의 결과는 원천 데이터와 설계에서 발생할 수 있는 오류를 식별하고, 이를 데이터 구축·검수 기준으로 구체화한 것이다.
