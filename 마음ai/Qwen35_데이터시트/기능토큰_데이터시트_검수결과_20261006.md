## 1. 판정

**현재 시트는 자연어 설명 응답을 학습하도록 작성되어 있어, 요청한 기능 토큰 학습용으로 구조를 변경해야 한다.**
발화와 근거 컨텍스트는 전환에 활용할 수 있다. 기존 자연어 정답은 모범 발화·TTS 문구 초안으로 활용하고, LLM 학습 정답은 별도의 기능 토큰과 인자 표현으로 다시 정의해야 한다.

| 검수 기준 | 실제 확인 결과 | 판정·조치 |
|---|---|---|
| 기능명·description·세부 파라미터·결과 반환 | 기능명과 입력 설명은 있으나 파라미터 타입·필수 여부·반환값 계약 없음 | 재설계 필요 |
| LLM 출력은 기능 토큰 | 160개 턴 모두 자연어 정답 | 전부 토큰 정답으로 전환 필요 |
| 토큰→기능→모범 발화→TTS 매핑 | token_id·실행 함수·반환 상태별 발화 매핑 열 없음 | 매핑 정의 필요 |
| 종료 토큰 | hs-end 표기는 0개이며 기능용 종료 규약 없음 | Qwen 대화 종료와 별도 기능 종료 규약 확정 필요 |
| description별 데이터 400개 | 현재 시나리오별 12~24개 대화 | 기능 확정 후 확대 필요 |
| 싱글턴 우선 | 싱글턴 80개, 멀티턴 40개 | 싱글턴 80개부터 전환·검수하고 멀티턴은 후속 단계로 유지 |
| 입력 발화 문장부호 금지 | 160개 턴 중 144개, 120개 대화 중 106개에 문장부호 존재 | 수정 필요 |
| 발화 다양성 | 존댓말·반말·짧은 발화·질문 구조 변형이 있음. 사투리 태그 0개 | 부분 충족, 사투리·현장 발화 추가 필요 |
| 완전히 동일한 중복 회피 | 원문 중복 0개, 문장부호·공백 제거 후 중복 0개 | 현재 기준 통과 |
| train:eval=8:2 | 100:20 = 83.3%:16.7% | 그룹을 유지하며 재분할 필요 |
| STT 오류 우선 | 태그 기준 16개 대화/120개 = 13.3%, 18개 턴. 전부 합성 | 실제 STT 사례 수집·오류 유형 확장 필요 |

원문 중복 검사는 user_text 전체 문자열 기준이며, 정규화 검사는 문장부호·공백 제거 및 영문 소문자 변환 기준이다. 의미상 유사 문장이 없다는 보장은 아니며, 같은 시드의 변형은 한 split에 유지해야 한다. 기능 단위 출력이 학습·양자화 이후 안정적으로 생성되는지는 이번 시트 검수로 확인한 사항이 아니다.

## 2. 기능 정의에 보완할 필드

현재 `01_기능정의`는 시나리오 분류에 가깝다. 다음 계약을 먼저 고정해야 기능 선택과 인자 추출을 검수할 수 있다.

| 항목 | 작성할 내용 |
|---|---|
| function_name | 실행 함수의 고유 이름 |
| description | 기능 목적, 실행 조건, 비슷한 기능과의 구분 |
| parameters | 인자명·타입·필수 여부·허용값·입력 출처·누락 시 행동 |
| returns | 반환값 구조와 성공·정보 부족·오류 상태 |
| output_token | 정답으로 출력할 기능 토큰 문자열 |
| argument_format | 인자를 출력할 경우의 순서·구분자·형식. 세션/백엔드에서 주입할 인자는 별도 명시 |
| end_token | 기능 명령 종료 표식과 생성 중지 조건 |
| token_id / tokenizer_revision | 최종 tokenizer에서 확인한 ID와 버전 |
| handler / tts_template_key | 토큰에 연결할 실행 함수와 반환 상태별 모범 발화 키 |
| seed_id / group_id | 증량 전 분할할 기준 발화·시나리오 가족 |

`description`을 적고 학습하는 것과 실제 함수 구현은 구분해야 한다. 모델은 기능/인자를 선택하고, 프로그램이 그 기능을 실행해 결과를 반환하며, 반환값으로 모범 발화를 완성한 뒤 TTS에 전달하는 구조로 정의한다.

예를 들어 다음은 설계 예시이며 확정 토큰이나 구현 완료 기능이 아니다.

```text
사용자 발화  무 잎 뒨면 어디를 찍어야 돼요
LLM 출력    <hs_recapture><hs-end>
프로그램    현재 진단의 재촬영 안내를 조회
반환값      region instruction status
모범 발화   반환된 instruction을 사용해 완성
TTS         완성된 안내를 음성으로 출력
```

이 예시의 대상 진단은 세션에서 결정하는 것으로 가정한다. 대상이 여럿이면 확인 기능이 필요하다. 작물·농약·부위를 사용자가 지정할 수 있는 기능에서는 인자 규약을 따로 정의해야 하며, 기능 토큰 하나만으로 인자가 자동 전달된다고 가정하지 않는다. 함수 실행 실패나 사용 정보 부족에도 각각 대응하는 모범 발화가 있어야 한다.

기존 assistant_text를 고정 TTS 문자열로 복사하면 다른 진단의 병명·점수가 남을 수 있다. 변경되는 병명·점수·안내 부위·농약 조건은 실제 반환값으로 채우고, 없는 값은 정보 부족 분기로 처리한다.

## 3. 수량과 분할

현재 값은 실행 기능별 수량이 아니라 주 시나리오별 대화 수이다.

| 현재 주 시나리오 | train | eval 후보(validation) | 합계 |
|---|---:|---:|---:|
| `disease_explanation` | 20 | 4 | 24 |
| `normal_explanation` | 10 | 2 | 12 |
| `recapture_guidance` | 15 | 3 | 18 |
| `followup_clarification` | 15 | 3 | 18 |
| `care_information` | 15 | 3 | 18 |
| `pesticide_information` | 15 | 3 | 18 |
| `scope_conflict` | 10 | 2 | 12 |
| 합계 | 100 | 20 | 120 |

기능당 400개를 train+eval의 전체 수량으로 해석하면 기능당 train 320개·eval 80개이다. 최종 기능이 F개면 총 400×F개가 필요하다. 현재 7개 시나리오를 그대로 7개 함수로 확정한 것은 아니다. 만약 '학습에만 400개'를 의미한다면 기능당 train 400개·eval 100개가 된다.

파일럿 전체 120개를 유지할 경우 96/24가 8:2이다. 먼저 싱글턴 80개만 전환한다면 64/16이 8:2이다. 단순히 마지막 행을 이동하지 말고 동일 기준 발화의 표현 변형·동일 진단/사진·연결 대화를 그룹으로 묶어 같은 split에 유지해야 한다. 수량은 턴 행 수가 아니라 대화 수로 계산했다.

멀티턴·다중 기능·parallel 출력은 인자 누락 확인, 이전 발화의 대상 유지, 다중 호출 순서·실패 반환 규약이 고정된 뒤 별도 단계로 확장한다. 현재 40개 멀티턴을 싱글턴으로 잘라 학습과 eval에 나누지 않는다.

## 4. 문장부호 수정 원칙

입력 발화 `user_text`에서 확인된 문장부호는 마침표 75개, 물음표 92개, % 1개, 가운데점 1개, 쉼표 1개이다. 문장부호가 없는 입력은 16개 턴이다.

문장 끝의 물음표·마침표는 제거할 수 있지만, 숫자 의미를 바꾸는 일괄 삭제는 피해야 한다. 예를 들어 '점수 0.87을 퍼센트로 읽으면 얼마야?'는 '점수 영 점 팔 칠을 퍼센트로 읽으면 얼마야' 같은 음성 발화로 바꾼다. 0.87에서 점만 삭제해 087로 만들면 의미가 달라진다.

문장부호 금지는 사용자 음성 발화 열에 적용한다. context_json의 따옴표·콜론·소수점, 토큰 표식의 괄호·하이픈, 학습 메시지 포맷의 구분자는 별도 규약이므로 같은 일괄 삭제 대상으로 취급하지 않는다. TTS 문구의 문장부호 사용은 음성 엔진과 별도 규칙으로 정한다.

부록 A에 수정 대상 144개 턴의 ID·행을 모두 기록했다.

## 5. STT 검수와 보완

현재 STT 태그 16개 대화 중 P_D004/P_D010/P_D022/P_N003/P_N012는 주로 띄어쓰기 변형이다. 나머지에는 뒨면·가상자리·모댈·질쏘·마죠 등의 합성 표현이 있지만 원 발화·음성·실제 STT 결과가 연결되어 있지 않아 실제 STT 대응 성능을 확인할 수 없다. STT 태그는 대화 단위로 상속된 경우가 있어 태그가 붙은 18개 턴 모두가 오류 발화인 것은 아니다.

| 우선 검수 사례 | 판단 |
|---|---|
| P_R003: 무 잎 뒨면 어디를 가까이 찍어야 돼요 | 현재 근거의 잎 뒷면 안내에 연결 가능. 재촬영 기능·부위 연결 사례로 유지 |
| P_R008: 배추 잎 맥 하고 가상자리 찍으라는 거죠 | 잎맥·가장자리 오인식 사례로 유지. 임의의 새 부위 인자를 만들지 않는지 검수 |
| P_F009: 그 모댈 버전 말구 숫자 칠삼이 머예요 | context에 0.73이 있어 현재 점수를 설명하지만, 칠삼을 무조건 0.73으로 바꾸는 규칙으로 증량하지 않음. 값이 없거나 후보 숫자가 여럿인 확인 사례 추가 |
| P_F017: 고추 가루 병 설명해주세요 | 입력에서 대상이 모호하고 진단이 없어 확인 질문이 타당. 확인 기능 토큰으로 전환 |
| P_P008: 제품 에이 물에 타는 양좀 알려 줘 | 발음식 제품명 사례. 확인된 희석 조건이 없는 현재 상태에서는 사용량을 반환하면 안 됨 |
| P_P011: 탄저병 약 찐하게 타면 더 잘 듣나 | 구어 표현 중심의 사례. 이것만으로 STT 오류 유형 커버리지를 충족했다고 집계하지 않음 |

보완할 유형은 병명 유사 발음, 작물명 혼동, 숫자·소수·단위, 부정어 누락, 단어 누락/삽입, 띄어쓰기, 사투리·발음 변형이다. 사투리와 띄어쓰기 변형은 그 자체로 STT 실패라고 단정하지 않고 각각 태그로 구분한다.

각 데이터에 원래 의도한 발화, 모델에 넣는 STT 결과, 실제/합성 구분, 오류 유형, 기대 기능, 기대 인자, 확인 필요 여부를 기록한다. 의미가 분명하고 context와 일치하면 같은 기능으로 연결하고, 기능이나 인자가 달라질 수 있으면 확인 기능으로 연결한다. 실제 STT 오류 로그로 별도 eval을 확보하며, 동일 원 발화의 STT 변형은 같은 split에 유지한다. STT 정상/오류 입력에서 기능 정확도와 인자 정확도·확인 행동을 따로 비교한다.

기능별 발화 400개는 존댓말·반말·짧은 발화·문장 구조·사투리·STT 유형별 목록을 먼저 만들고 증량한다. 같은 뜻의 표현 변형은 필요하지만 완전히 같은 문장은 중복으로 만들지 않는다.

## 6. 토큰·EOS·양자화에서 확인할 사항

`<hs-end>`나 `<hs_recapture>`를 문자열로 적는 것만으로 tokenizer의 단일 토큰으로 등록되는 것은 아니다. 새 특수 토큰을 사용하는 경우 tokenizer 등록과 모델 임베딩 크기 정합, 추가 토큰의 학습·저장 범위를 확인해야 한다. Transformers는 새 토큰 추가 시 임베딩 크기를 맞추도록 안내하며, PEFT는 추가 토큰 학습을 위한 trainable_token_indices를 제공한다. [Tokenizer 공식 문서](https://huggingface.co/docs/transformers/main_classes/tokenizer), [PEFT LoRA 공식 문서](https://huggingface.co/docs/peft/main/package_reference/lora)

기능용 hs-end 표식과 Qwen chat template의 대화 종료는 구분해 설계한다. 토큰 표식을 출력했다고 생성이 자동 중지된다고 가정하지 말고, 최종 tokenizer·모델·생성 설정에서 정답 직렬화와 중지 조건을 확인한다. [Qwen3.5-2B 공식 템플릿](https://huggingface.co/Qwen/Qwen3.5-2B/blob/main/chat_template.jinja)

하드코딩할 숫자 ID는 현재 임의로 정하지 않는다. 확정한 tokenizer revision에서 토큰→ID를 추출하고, 학습 모델·병합 모델·변환기·실제 보드 실행에서 같은 매핑인지 확인한 뒤 버전과 함께 고정한다. 새 토큰을 추가한 모델을 제공 RKLLM 도구가 변환·실행하는지는 실제 패키지 확인과 최소 예제로 검증해야 한다. 현재 그 결과는 없다.

특수 토큰은 skip_special_tokens=True로 디코딩하면 생략될 수 있으므로, 기능 라우터가 생성 ID를 읽을지 토큰 문자열을 유지할지도 규약에 포함한다. Qwen 모델 크기와 revision이 아직 미확정이라 현 단계의 실제 token_id는 미정이다.

## 7. 다음 수정 순서

1. 실제로 필요한 함수 목록과 description·파라미터·반환 상태를 확정한다.
2. 기능 토큰·인자 표현·hs-end·TTS 반환값 매핑을 정의한다.
3. 기존 싱글턴 80개를 새 구조로 전환하고 문장부호·STT 사례를 우선 검수한다.
4. 기준 발화/시나리오 그룹을 8:2로 분할한 뒤 기능당 400개로 증량한다.
5. 기능 선택·인자·출력 포맷·종료·STT 정상/오류·TTS 매핑을 eval에서 검증한다.
6. 싱글턴을 통과한 후 멀티턴·다중 기능·parallel을 별도 버전으로 확장한다.
