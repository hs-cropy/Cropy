# Cropy Qwen3.5 데이터시트 검수 매뉴얼

작성자: 김헌영<br>
작성일: 2026년 10월 6일<br>
적용 대상: 기능 토큰 학습용 싱글턴 데이터와 이후 확장 데이터

## 1. 이 매뉴얼의 목적과 적용 범위

검수자는 **사용자 발화를 읽고 올바른 기능과 인자를 선택했는지**, **근거에 맞는 반환 상태와 음성 답변을 연결했는지** 확인한다. 수량을 채웠다는 이유나 자동 검사에 오류가 없다는 이유만으로 승인하지 않는다.

원본 구축 기준 파일은 [전체 기능 400개 초안 v5](Qwen35_데이터시트/Cropy_Qwen35_전체기능400_초안_v5.xlsx)이다. 7개 기능이 각각 싱글턴 400개로 구성됐으며, 기능별 학습 320개·검증 80개, 전체 학습 2,240개·검증 560개로 총 2,800개다. 멀티턴 40개는 보류 상태다. 신규 6개 기능의 확장 데이터는 `draft`이며, 기존 농약 AI 검수의 `reviewed`·`rejected` 기록을 보존했다. 사람 최종 승인 수량은 0개다. 초안 구축은 토큰 ID 등록·실제 학습·모델 평가·기능 및 TTS 실행 완료를 뜻하지 않는다. [v5 구축 결과](Qwen35_데이터시트/전체기능400_구축결과_v5.md)의 범위와 한계를 함께 확인한다.

2026-10-08 정답 수정 후 재검수 작업본은 [정답 변경본 v7](Qwen35_데이터시트/Cropy_Qwen35_정답변경본_v7.xlsx)이다. 위 v5 설명은 원본 구축 시점의 상태다. v7은 불합격 164개를 수정해 `draft`로 되돌리고 나머지 2,636개에 v6 AI 검수 기록을 연결했다. 기존 보류 판정 397개와 수정 행 12개에 겹친 별도 보류 사유는 유지했다. 사람 승인 0개이며 전체 학습 2,240개·검증 560개를 보존했다. 기능 정답 변경으로 기능별 실제 수량은 진단 405개, 예측 지표 406개, 재촬영 400개, 관리 399개, 농약 397개, 추가 질문 393개, 범위 제한 400개다. `01_기능정의`에서 실제 수량과 승인 수량을 구분하고, [v7 수정 내역 및 저장 확인](Qwen35_데이터시트/정답변경본_v7_수정내역.md)을 읽은 뒤 변경 행부터 재검수한다. 자동 저장 검증 통과를 의미 검수 통과로 처리하지 않는다.

2026-10-08 재검수 및 수량 조정 결과는 [v8 결과 보고서](Qwen35_데이터시트/v8_재검수_보류검토_수량조정_결과.md)를 확인한다. 수정 164개 중 156개는 기존 결함을 정리했고 8개는 별도 보류 사유가 남았다. 기존 보류 397개 중 290개는 해당 사유를 해결했고 107개는 추가 확인이 필요하다. 남은 보류는 총 115개다. 기능별 활성 초안은 각각 학습 320개·검증 80개로 맞췄으며 초과 13개는 singleton_reserve로 보존하고 부족한 기능에 신규 draft 13개를 추가했다. 사람 승인 수량은 0개다. AI 검수를 사람의 독립적인 의미 검수나 최종 승인으로 해석하지 않는다. 신규 13개는 발화·근거·정답을 별도로 검수한다.

2026-10-08 현재 검토 작업본은 [신규 검수 및 보류 정리 v9](Qwen35_데이터시트/Cropy_Qwen35_신규검수_보류정리_v9.xlsx)이다. 신규 13개는 AI 의미 검토 문제 미발견으로 reviewed 기록을 남겼다. 기존 보류 115개 중 113개는 수정 후 AI 재검토했고 P_R015·STT_027 두 복합 요청은 보류를 유지했다. STT 타당성 보류 63개와 사투리 10개는 일반 발화로 새로 작성했으며 실제 STT·지역 화자 검증 완료로 집계하지 않는다. 기능별 초안320/80과 사람 승인0은 유지했다. [v9 행별 판정과 한계](Qwen35_데이터시트/v9_신규13_보류115_검수결과.md)와 [학습 준비 점검](Qwen35_데이터시트/v9_Qwen35_Colab_학습준비_점검.md)을 확인한다. 모호한 높음·정도 표현이 점수인지 심각도인지 실제 피해인지 정해지지 않으면 clarify_request target=topic으로 항목부터 확인한다.

기능당 400개는 **학습과 검증을 합친 대화 수**다. 원문과 그 STT·사투리 변형도 대화 수에 포함되지만, 서로 다른 의도 400종이나 실제 음성 400건으로 설명하면 안 된다.

## 2. 판정 원칙

| 판정 | 엑셀에 기록할 상태 | 기준 | 학습 데이터로 내보내기 |
| --- | --- | --- | --- |
| 미검수 | `draft` | 사람 검수를 아직 하지 않음 | 제외 |
| 보류 | `reviewed` | 검토했지만 의도·근거·라벨을 확정하지 못함. 메모에 `판정 보류`와 필요한 확인을 기록 | 제외 |
| 통과 | `approved` | 해당 대화의 모든 턴이 아래 기준을 충족하고 검수자·검수일·근거가 기록됨 | 다른 내보내기 조건도 충족한 경우에만 포함 |
| 불합격 | `rejected` | 기능·인자·근거·토큰·분할 등에 확인된 결함이 있음 | 제외 |

**필수 항목 하나라도 틀리면 불합격이다.** 확인이 필요한 사실을 확인하지 못한 경우는 보류다. 좋은 항목이 많더라도 잘못된 농약 수치나 정답 누출 같은 결함을 상쇄할 수 없다.

불합격 데이터는 원인을 고친 뒤 `draft`로 되돌리고 재검수한다. 보류 데이터도 추가 확인이나 수정 후 다시 판정한다. 수정한 행을 이전 승인 상태로 방치하지 않는다.

데이터 검수의 통과와 모델의 정답 여부는 별개다. 데이터의 정답이 올바른지 먼저 승인하고, 모델이 그 정답을 출력했는지는 `05_평가결과`에서 별도로 평가한다.

## 4. 실제 검수 순서

1. 기준 파일을 복사해 검수 작업본을 만든다. 파일 버전과 담당자를 기록한다.
2. `record_type=data`, `phase=singleton`인 대화부터 검수한다. `example`, `EX_` 예시, 빈 행, `multiturn_deferred`, `singleton_reserve`는 현재 싱글턴 학습 대상에서 제외한다. 예비 행은 삭제하지 않으며 다시 활성화할 때 기능별 수량과 그룹 분할을 확인한다.
3. ID 중복·문장부호·JSON 오류·연결 누락·그룹 분할 충돌을 먼저 검사한다. 자동 검사에서 찾은 결함을 표시하되, 자동 통과를 사람 승인으로 바꾸지 않는다.
4. 처음에는 질문 유형별로 정상 발화·STT·사투리·정보 부족 사례를 골라 기준을 맞춘다. 검수자가 여럿이면 같은 사례를 각자 판정하고, 의견이 다른 이유를 기록한다.
5. **정답 토큰을 보기 전에** `user_text`와 `context_json`을 읽고 예상 기능·인자를 적는다. 답을 미리 보고 발화를 억지로 해석하지 않는다.
6. `canonical_utterance`와 비교해 STT·사투리 변형이 의도를 유지하는지 확인한다. 원래 의도는 검수용 정보이며 모델 입력에 추가하지 않는다.
7. `function_name`, `arguments_json`, `llm_output`이 자신의 판정과 일치하는지 확인한다.
8. 근거를 읽고 `expected_return_status`, `clarification_needed`, TTS 키와 참고 답변을 판정한다.
9. 같은 `scenario_group_id`와 `seed_id`의 다른 변형을 함께 확인한다. 같은 원문 가족이 학습과 검증에 나뉘지 않았는지 확인한다.
10. 승인할 모든 대화를 전수 검수한다. 표본 검수 결과만으로 나머지 대화를 일괄 승인하지 않는다.
11. `04_검수분할`에 검수자·판정·메모·검수일을 기록한다. 수정한 경우 영향받는 변형과 평가 정답도 재확인한다.
12. 저장 후 다시 열어 수량·수식·분할·승인 상태를 확인한다. 승인된 대화만 추려 내보내기 조건을 마지막으로 검사한다.

## 5. 항목별 통과·불합격 기준

### 5.1 기본 구조와 연결

| 검사 항목 | 통과 | 불합격 |
| --- | --- | --- |
| 대화 ID와 턴 | `conversation_id + turn_index`가 고유하고 턴 순서가 유효함 | 같은 키 중복, 누락된 턴, 순서 오류 |
| 현재 학습 범위 | 싱글턴이며 검수·분할 정보가 연결됨 | 멀티턴을 잘라 싱글턴으로 수량에 포함하거나 예시를 학습 데이터로 사용 |
| 컨텍스트 | 참조 ID가 존재하고 JSON 문법·값 타입이 유효함 | 없는 ID, 깨진 JSON, 다른 대화의 근거 연결 |
| 근거 출처 | 실제·합성·사람 구성 자료를 정확히 표시함 | 합성 자료를 실제 API 기록·공식 확인 자료로 표시 |
| 필수값 | 기능·인자·정답·반환 상태·TTS 키 등 해당 사례의 필수값이 있음 | 필요한 값이 비어 있거나 서로 충돌함 |

실제 정보가 없는 상태를 의도적으로 표현한 `null`·빈 목록은 결함이 아니다. 단, **없는 정보에 맞는 반환 상태와 답변**이어야 한다. 숫자 `0`, 누락된 키, `null`, 빈 목록을 같은 뜻으로 취급하지 않는다.

### 5.2 입력 발화와 다양성

| 검사 항목 | 통과 | 불합격 |
| --- | --- | --- |
| 문장부호 | `user_text`, `canonical_utterance`에 문장부호·불필요한 특수기호가 없음 | 물음표·마침표·쉼표·퍼센트 기호 등을 모델 입력에 그대로 사용 |
| 숫자 의미 | 소수·수량·단위를 읽는 발화로 바꾸고 원래 의미를 유지함 | `0.87`을 `087`로 만드는 등 의미를 바꾸는 삭제 |
| 자연스러움 | 실제로 말할 수 있는 문장이고 기능 의도를 해석할 수 있음 | 어색한 단어 조합, 억지 사투리, 의미 없는 오타로 수량만 늘림 |
| 동일 발화 | 완전히 동일한 입력이 중복되지 않음 | 동일 입력을 ID만 바꾸어 반복함 |
| 표현 다양성 | 반말·존댓말·질문 구조·현장 상황·STT·사투리를 구분해 구성함 | 접두어만 붙이는 식의 변형을 독립적인 상황 다양성으로 설명함 |

문장부호 제한은 **음성 입력 발화 열**에 적용한다. JSON의 따옴표·콜론, 토큰의 `< >`와 하이픈, TTS 템플릿의 placeholder는 제거하지 않는다. TTS 문장부호는 음성 출력용 별도 규칙이다.

완전 동일 중복 외에도 공백 제거·영문 소문자 변환 후 같은 문장은 재확인한다. 의도적으로 만든 띄어쓰기 STT 변형은 원문 가족과 목적을 기록해 유지할 수 있지만, 서로 다른 독립 원문으로 집계하지 않는다.

### 5.3 기능과 인자 선택

기능은 **사용자의 요청과 현재 컨텍스트**로 선택한다. 정보가 부족하다는 이유만으로 무조건 확인 기능을 선택하지 않는다. 요청 대상은 분명하지만 조회할 값이 없으면 해당 조회 기능의 정보 부족 반환이 적절하다.

| 사용자 의도 | 기대 기능 | 통과 조건 |
| --- | --- | --- |
| 진단 후보·정상 의미·심각도 속성 등 설명 | `get_diagnosis` | 실제 측정·확진·피해량을 임의로 만들어 설명하지 않음 |
| 점수·후보 순위·분포·비교 | `get_prediction_metrics` | 점수를 실제 발병 확률이나 피해 비율로 바꾸지 않음 |
| 저장된 재촬영 부위·이유·지침 | `get_recapture_guidance` | 현재 근거의 안내와 부위를 사용함 |
| 제공된 원인·예방·관리 자료 | `get_care_information` | 자료의 일반 항목을 현장 원인이나 효과 보장으로 바꾸지 않음 |
| 농약 목록·조건·검증·비교·혼용 | `get_pesticide_information` | 질문 유형과 제품 지칭을 구분하고 없는 조건은 만들지 않음 |
| 작물·병명·제품·점수·발화 의도가 모호함 | `clarify_request` | 무엇을 확인해야 하는지 `target`이 맞음 |
| 미지원 작물·실행 요청·입력 범위 | `handle_scope_limit` | `reason`이 맞고 실제 실행했다고 말하지 않음 |

인자는 `01_기능정의`의 필수값·타입·enum에 맞아야 한다. 정의에 없는 인자나 값, 모델이 임의로 만든 진단 ID는 불합격이다. 현재 진단 대상은 백엔드 세션의 값으로 연결한다.

농약 기능에는 `topic`, `product_ref`가 모두 필요하다.

| `topic` | 구분할 질문 |
| --- | --- |
| `list` | 현재 연결된 제품 목록 |
| `dilution` | 희석 배수·물과 약의 양·농도 |
| `usage` | 처리 방법·부위·시기·횟수·간격 |
| `phi` | 사용 후 수확까지 기다릴 기간 |
| `reentry` | 처리 구역에 사람이 다시 들어갈 조건 |
| `verification` | 등록 확인·출처·검증 상태·동기화 시각 |
| `ingredient` | 유효 성분·성분 함량 |
| `summary` | 현재 제품 자료의 확인된 내용과 한계 요약 |
| `checklist` | 제품 표시와 공식 자료에서 확인할 항목 목록 |
| `comparison` | 여러 제품의 효과 비교 |
| `mixing` | 여러 제품의 혼용 가능 여부 |

`product_ref=current`는 **유일하게 식별된 현재 제품**을 뜻한다. 첫 번째 제품을 자동으로 고르는 뜻이 아니다. 목록 전체 조회·전체 비교·혼용 요청에는 `all`을 사용한다. 여러 후보 중 “그 약”이 어느 제품인지 알 수 없으면 `clarify_request`, `target=product`가 맞다. 이 사례를 농약 기능 400개 수량에 맞추려고 조회 기능으로 억지 라벨링하면 불합격이다.

### 5.4 STT 오류와 사투리

| 검사 항목 | 통과 | 불합격 |
| --- | --- | --- |
| 의도 보존 | 오류 발화가 원래 요청과 같은 기능·인자를 뜻하거나, 모호함을 확인 요청으로 처리함 | 바뀐 의미를 무시하고 원래 정답을 강제로 유지 |
| 발음식 표기 | 병명·제품명·부위·숫자의 가능한 인식 변형이며 컨텍스트와 함께 해석 가능 | 무작위 글자를 바꾸거나 근거 없이 제품·병명을 확정 |
| 부정어 | “안 써도 되나요”처럼 부정이 있는 요청의 의미를 구분함 | 부정어가 빠져 의미가 달라졌는데 같은 정답으로 취급 |
| 숫자와 단위 | 문맥상 유일한 값에 연결하거나, 여러 해석이 가능하면 확인함 | “칠삼”을 언제나 `0.73`으로 자동 확정 |
| 사투리 | 자연스럽고 뜻이 유지되며 사투리 변형으로 표시함 | 억지 표현을 사용하거나 사투리를 실제 STT 오류로 오인해 표시 |
| 출처 | 실제 STT와 합성을 구분함. 실제 사례는 확인 가능한 음성 출처·접근 기록을 연결함 | 합성인데 실제 STT로 표시하거나 없는 음성 자료를 있다고 기록 |

**모호한 발화도 통과할 수 있다.** 다만 정답이 올바른 확인 기능이어야 한다. 검수자가 `canonical_utterance`를 보고서만 뜻을 알 수 있는 경우, 실제 모델에는 그 의도 정보가 없다는 점을 고려해 판정한다.

예를 들어 “고추 가루병 설명해줘”에서 병명을 정할 컨텍스트가 없다면 확인 요청이 통과다. “칠삼이 뭐예요”에서 후보 숫자가 여러 개라면 점수 설명으로 단정한 정답은 불합격이다.

### 5.5 정답 토큰

현재 싱글턴 정답은 **기능 토큰 1개 → 정해진 인자 토큰 → 종료 토큰 1개** 순서다. 토큰 사이에 자연어·JSON·설명·다른 기능 호출을 넣지 않는다.

```text
통과 예시
<hs_get_pesticide_information><hs_topic_dilution><hs_product_current><hs-end>

불합격 예시 종료 토큰 없음
<hs_get_pesticide_information><hs_topic_dilution><hs_product_current>

불합격 예시 자연어 섞임
희석량을 확인하겠습니다 <hs_get_pesticide_information><hs_topic_dilution><hs_product_current><hs-end>
```

다음 중 하나라도 해당하면 불합격이다.

- `06_토큰매핑`에 없는 문자열을 사용한다.
- 기능명·인자 JSON·정답 토큰이 서로 다르다.
- 필수 인자가 빠지거나 인자 순서·enum이 다르다.
- `<hs-end>`가 없거나 여러 번 나오거나 종료 뒤에 다른 출력이 붙는다.
- 현재 싱글턴 규약에 다중 기능·parallel 출력을 넣는다.

문자열 검수 통과는 실제 단일 token ID 검증 완료를 뜻하지 않는다. `<hs-end>`와 Qwen의 기본 EOS도 같은 것으로 취급하지 않는다.

### 5.6 반환 상태와 근거

| `expected_return_status` | 통과하는 상황 | 불합격하는 상황 |
| --- | --- | --- |
| `ok` | 요청에 대해 근거로 확인할 수 있는 내용을 반환함 | 없는 값이나 미검증 조건을 성공 반환으로 표시 |
| `needs_clarification` | 기능·대상·인자를 정하려면 추가 확인이 필요함 | 대상이 모호한데 임의로 제품이나 병명을 선택 |
| `insufficient_information` | 요청은 분명하지만 답할 근거가 없거나 요구된 검증 조건이 충족되지 않음 | 정보가 없는데 수치·효과·혼용 가능 여부를 추정 |
| `unsupported_scope` | 현재 지원 범위 밖의 요청임 | 미지원 요청을 수행·지원한 것처럼 처리 |

`ok`는 “농약을 써도 된다”는 뜻이 아니다. 예를 들어 검증 상태를 조회해 **미검증임을 정확히 반환**하는 사례나 표시사항의 **확인 항목 목록**을 반환하는 사례는 `ok`일 수 있다.

현재 백엔드에서 농약 사용 조건의 검증 여부는 다음 세 필드를 함께 확인한다. 이는 프로젝트의 구현 기준이며 법적 사용 허가를 대신하는 판정이 아니다.

- `verification_status`가 `verified`다.
- `source`가 `PSIS`다.
- `synced_at`이 존재한다.

세 조건이 맞더라도 **현재 작물·병해·제품에 연결된 자료인지**와 **답하려는 필드가 실제로 있는지**를 추가로 확인한다. 날짜가 있다는 사실만으로 최신성을 보장하지 않는다. 특정 날짜까지 최신이라고 답하려면 그 주장에 맞는 확인 근거가 필요하다.

확인할 주요 필드는 `pesticides[].dilution`, `usage`, `active_ingredient`, `safety.phi_days`, `safety.reentry_hours`다. 성분 정보가 있다는 사실만으로 사용 조건까지 검증됐다고 해석하지 않는다. 효과 비교와 혼용은 제품 두 개가 목록에 있다는 이유로 판단하지 않는다.

현재 농약 확장의 신규 사용 조건·성분·효과 비교·혼용 사례에는 실제 확인 값이 없다. 이 상태에서 숫자나 가능 여부를 넣으면 불합격이다. 합성 자료를 사람 검수자가 공식 확인 자료로 바꾸어 표시해서도 안 된다.

### 5.7 TTS 연결

| 검사 항목 | 통과 | 불합격 |
| --- | --- | --- |
| 템플릿 연결 | `tts_template_key`가 존재하고 기능·인자·반환 상태에 맞음 | 없는 키, 다른 상태의 템플릿 연결 |
| 동적 값 | 병명·점수·제품명·사용 조건을 현재 반환값으로 채우도록 설계됨 | 다른 사례의 값을 고정해서 재사용 |
| 근거 누락 | 필수값이 없으면 정보 부족 또는 확인 질문으로 전환함 | 빈 placeholder를 그대로 읽거나 임의 값으로 채움 |
| 안내 내용 | 사용자의 요청에 대응하며 근거의 한계를 유지함 | 분류를 확진으로 말하거나 없는 농약 조건·효과를 단정 |
| 참고 답변 | `tts_text_draft`가 해당 사례의 근거와 일치함 | 토큰은 맞는데 참고 답변에 근거 없는 내용이 들어 있음 |

`tts_text_draft`는 참고 답변이고 실제 런타임 구현 완료의 증거가 아니다. 템플릿을 검토한 것과 실제 TTS로 재생해 확인한 것을 구분해서 기록한다.

### 5.8 분할·수량·정답 누출

| 검사 항목 | 통과 | 불합격 |
| --- | --- | --- |
| 그룹 유지 | 같은 원문·시드·진단·사진에서 연결된 변형이 같은 split에 있음 | 한 원문의 정상 발화는 train, STT 변형은 validation으로 배치 |
| 검증용 원문 | 학습 원문을 조금 바꿔 이동한 사례가 아니며 그룹이 분리됨 | 평가 수량을 맞추려고 원문 가족 일부만 이동 |
| 수량 | 현재 승인된 싱글턴 대화를 기준으로 기능별 집계함 | 턴 수·예시·보류 멀티턴·불합격 행을 합쳐 400개라고 표시 |
| 8대2 | 기능당 400개 목표를 완료했다면 승인 대화 train 320·validation 80 | draft 수량만으로 승인된 학습 데이터 400개를 확보했다고 주장 |
| 모델 입력 | 사용자 발화와 필요한 근거 JSON, 기능 계약을 사용함 | 정답 기능·토큰·반환 상태·TTS 답변·질문 유형이 들어 있는 검수 ID를 입력에 포함 |
| 검증 관리 | validation은 모델 선택·평가용으로 관리함 | validation을 학습 또는 양자화 calibration 자료로 사용 |

외부 검수용 `conversation_id`, `scenario_group_id`, `seed_id`, `split`, `canonical_utterance`, 정답 열, 검수 메모를 모델 입력에 넣지 않는다. **질문 유형이 드러나는 그룹 ID를 `context_json` 안에 넣는 것도 정답 누출**이다. 함수 description과 전체 허용 인자 목록은 계약 정보이므로, 해당 행의 정답 라벨을 제공하는 것과 구분한다.

검증 결과를 보고 수정한 데이터를 아무 기록 없이 같은 최종 시험에 계속 사용하지 않는다. 개발용 validation과 추후 별도로 확보할 최종 test의 용도를 구분한다. 그룹 제약 때문에 비율이 맞지 않으면 원문 가족을 쪼개지 말고 그룹 단위 수량 구성을 조정한다.

## 6. 통과·불합격 사례를 판정하는 방법

아래 사례는 검수 설명용이며 실제 제품의 사용 조건을 안내하는 예시가 아니다.

| 발화와 상황 | 통과하는 정답 | 불합격하는 정답 |
| --- | --- | --- |
| `이 재품 히석 기준 알려주세여` 유일한 제품이 있지만 희석 정보는 없음 | 농약 `dilution/current`, 정보 부족 반환 | 없는 희석 배수를 만들어 TTS에 넣음 |
| `그 약 얼마나 타요` 후보가 여러 개이고 제품을 구분할 근거가 없음 | 확인 기능 `target=product` | 첫 제품을 current로 선택 |
| `밭에 다시 들어가는 시간을 알려주세요` 현재 제품이 유일함 | 농약 `reentry/current`, 근거에 맞는 반환 상태 | 수확 제한 `phi`로 연결 |
| `수확 며칠 전까지 쓰는지 확인해주세요` 현재 제품이 유일함 | 농약 `phi/current`, 근거에 맞는 반환 상태 | 재진입 시간으로 답변 |
| `보이는 두 약 한 통에 섞어도 되나요` 혼용 근거 없음 | 농약 `mixing/all`, 정보 부족 반환 | 목록에 있으므로 혼용 가능이라고 답변 |
| `제품명이 보이면 검증된 거죠` 상태가 미검증으로 확인됨 | 농약 `verification/current`, 미검증 상태를 정확히 설명 | 검증 완료라고 설명 |
| `칠삼이 뭐예요` 연결 가능한 숫자나 대상이 여러 개임 | 숫자·발화 의미에 맞는 확인 기능 | 무조건 0.73이라고 설명 |
| `고추 가루병 설명해줘` 병명을 정할 근거가 없음 | 확인 기능의 적절한 `target` | 임의로 특정 병명을 선택 |
| `물을 자동으로 주고 기록도 저장해줘` 실행 기능 미지원 | 지원 범위 안내 `reason=action` | 실제로 실행·저장했다고 답변 |

정보 부족 사례와 모호한 사례는 실패 데이터가 아니라 필요한 학습 사례다. **올바른 대응이 정답으로 지정돼 있으면 통과**다.

## 7. 검수 기록 작성 방법

최종 판정은 `04_검수분할`에 대화 단위로 기록한다. `07_STT검수`와 `09_농약확장검수`의 메모만 바꾸고 대화를 승인한 것으로 처리하지 않는다.

| 기록 칸 | 작성 방법 |
| --- | --- |
| `author` | 기존 작성자를 보존한다. 현재 작성자는 김헌영이다 |
| `reviewer` | 실제 검수한 담당자의 이름을 적는다. 작성자 이름을 자동 복사하지 않는다 |
| `review_status` | `draft`, `reviewed`, `approved`, `rejected` 중 실제 판정에 맞게 선택 |
| `review_notes` | 검수 항목, 판정 근거, 수정 내용, 재검수 필요 여부를 남김 |
| `reviewed_at` | 실제 검수한 날짜를 기록함 |

가능하면 작성자와 다른 검수자가 확인한다. 동일인이 검수한 경우 실제 담당자 이름을 쓰고 메모에 자기 검수임을 기록한다. 자동 검사 실행만으로 사람 이름·검수일·승인 상태를 채우지 않는다.

메모는 “확인 완료” 한 줄 대신 다음 형식으로 남긴다.

```text
[통과] 의도·함수·인자·토큰 일치
근거에 희석 조건이 없어 insufficient_information이 맞음
STT 변형 의미 유지 그룹과 분할 확인 TTS에 임의 수치 없음
```

## 9. 단계별 최종 통과 조건

### A. 데이터 검수 통과

- [ ] 현재 대상 대화가 싱글턴이고 예시·빈 행이 아니다.
- [ ] 발화의 의미·자연스러움·문장부호·중복을 확인했다.
- [ ] STT·사투리의 의미와 출처를 확인했다.
- [ ] 기능·인자·토큰·종료 표식이 일치한다.
- [ ] 컨텍스트와 반환 상태·TTS가 일치하고 없는 내용을 생성하지 않는다.
- [ ] 원문 가족의 분할이 유지되고 모델 입력에 정답 누출이 없다.
- [ ] 수정 후 연결된 변형·평가 정답·수량을 다시 확인했다.
- [ ] 실제 검수자·검수일·판정 근거를 기록했다.

모두 충족하면 `approved`다. 토큰 ID가 미등록이라는 이유만으로 의미 검수 자체를 하지 못하는 것은 아니다. 다만 이 승인만으로 실제 학습 준비가 완료되지는 않는다.

### B. 기능 토큰 학습에 사용할 준비 완료

- [ ] 승인된 싱글턴만 내보내고 `example`, 보류·불합격·미검수·보류 멀티턴을 제외했다.
- [ ] 기능당 400개 완성본을 사용할 경우 승인 수량이 학습 320개·검증 80개다. 초안 수량과 승인 수량을 구분했다.
- [ ] 학습·검증 그룹이 분리돼 있고 validation을 학습·calibration에 넣지 않았다.
- [ ] 확정 모델·tokenizer·chat template 버전을 기록했다.
- [ ] 기능·인자·종료 문자열의 실제 token ID와 토큰 순서를 검증했다.
- [ ] 토큰 추가에 따른 모델 입력·출력 임베딩과 tokenizer 저장 상태를 확인했다.
- [ ] 기능 종료 표식과 기본 EOS, 생성 중단 규약을 구분해 확인했다.
- [ ] 모델 입력과 정답 출력을 실제 학습 메시지 형식으로 변환하고 정답 누출이 없는지 확인했다.

작은 파일럿으로 먼저 학습한다면 실제 승인 수량과 실험 범위를 그대로 기록한다. 이를 기능당 400개 완성본 학습이라고 표시하지 않는다. 기능 handler나 실제 TTS 구현 완료는 기능 선택 모델의 학습 준비와 별도 단계다.

### C. 실제 기능·음성 서비스에 사용할 준비 완료

- [ ] 모델 출력 parser가 기능·인자·종료 토큰을 검사하고 잘못된 출력을 실행하지 않는다.
- [ ] 실제 handler가 올바른 대상과 반환 상태·값을 제공한다.
- [ ] 성공·정보 부족·확인·미지원·실행 실패 상황에서 적절한 음성 안내가 나온다.
- [ ] TTS placeholder가 현재 반환값으로 채워지고 누락된 값을 임의로 생성하지 않는다.
- [ ] 실제 모델 평가 결과와 기능 실행·TTS 재생 결과를 기록했다.
- [ ] 양자화·변환 후 tokenizer 버전과 실제 token ID·매핑·종료 동작을 다시 확인했다.

이 단계의 실행 실패 대응은 배포 구현에서 별도로 확인한다. 현재 데이터의 반환 상태 enum에 임의로 새 상태를 추가하지 않는다. 양자화 산출물에서 확인하지 않은 ID를 하드코딩하지 않는다.

## 10. 농약 400개 검수에서 먼저 확인할 항목

1. `phi`와 `reentry`, 제품 `current`와 `all`을 혼동한 사례가 없는지 확인한다.
2. 정보 부족인 희석·사용·성분·비교·혼용 요청에 임의 값이나 가능 여부가 들어 있지 않은지 확인한다.
3. 신규 STT 128개와 사투리 111개의 의미 보존·자연스러움을 원문 가족 단위로 검수한다.
4. 컨텍스트 안의 지시문을 사용자 요청이나 시스템 규칙으로 따른 사례가 없는지 확인한다.
5. 농약 검증 80개가 학습 원문 가족과 섞이지 않았는지 확인한다.
6. 통과한 대화부터 실제 검수 기록을 작성한다. 전수 검수가 끝나기 전 400개 전체를 일괄 승인하지 않는다.

모든 기능은 현재 수량 목표를 채운 **초안**이다. 농약의 기존 불합격 13개·보류 23개를 해결하고, 신규 6개 기능도 같은 매뉴얼로 전수 의미 검수한다. 사람 검수 후 실제 승인 수량과 유형별 결손을 확인한다. 자동 형식 검사 통과만으로 2,800개 전체를 승인하지 않는다.

2026-10-06 [전체 2,800개 AI 검수 기록](Qwen35_데이터시트/전체2800_매뉴얼기반_AI검수_v6.md)은 불합격 164개·보류 397개·AI 검토 문제 미발견 2,239개다. 별도 검수표의 문제 미발견도 사람 승인 전 `reviewed`로 기록한다. 정답을 이미 본 작성 모델의 검수이므로 독립 블라인드 사람 검수를 대신하지 않는다. 행별 사유에 따라 원본의 관련 시트를 수정·재검수하고, 독립 검수자가 사용자 발화와 필요한 근거부터 판정한 뒤 정답을 대조한다.

## 2026-10-08 v10 복합 요청 및 사람 검수 안내

현재 수정본은 `Qwen35_데이터시트/Cropy_Qwen35_복합요청정리_v10.xlsx`입니다. 복합 요청 P_R015와 STT_027은 `clarify_request`의 `target=topic`으로 먼저 처리할 항목을 묻습니다. 여러 기능을 한 번에 실행하는 정답으로 승인하지 않습니다. 전체 2,800개와 train 2,240·validation 560은 유지되며 clarify_request는 402개, get_recapture_guidance는 398개로 변경됐습니다. 다른 5개 기능은 각각 400개입니다. 사람 승인 수량은 0개입니다.

사람 검수는 익명 사례 129개의 `Cropy_Qwen35_사람검수표_v10.xlsx`를 사용합니다. 먼저 A–C의 발화·근거와 기능 계약을 읽고 D–I에 독립 판정·실제 사람 이름·검수일을 기록합니다. 이후 별도 `v10_사람검수_대조용정답.csv`와 case_id로 대조하고 J–L에 대조일·최종 판정·근거를 기록합니다. 독립 기능·인자·반환 상태가 정답과 일치하고 기존 의미·STT·근거·TTS 기준을 모두 충족할 때만 approved로 기록합니다. 모호함은 reviewed, 오류는 rejected로 남깁니다. 작성 AI의 reviewed를 사람 승인으로 바꾸지 않습니다.

원본 정답을 변경하면 해시 연결이 달라지므로 검수표와 대조 정답을 갱신하고 재검수합니다. 이 129개 검수는 전체 2,800개의 사람 검수 완료를 의미하지 않습니다. Colab 파일럿은 7개 기능마다 train·validation 승인 사례가 있어야 시작합니다. 검수 및 Colab 사용 안내 (로컬 자료, 이 PR 미포함: `Qwen35_데이터시트/Colab_파일럿_v10/README.md`)를 따릅니다.
